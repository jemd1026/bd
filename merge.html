1. ¿Qué es MERGE?

MERGE es una sentencia SQL que permite realizar tres operaciones en una sola instrucción: insertar registros nuevos, actualizar los existentes y eliminar los que ya no corresponden.

La idea central es comparar una tabla origen (la fuente de datos nueva) contra una tabla destino (la que queremos mantener actualizada), y aplicar automáticamente lo que corresponda según el resultado de esa comparación.

Analogía: Imagina que tienes una lista de empleados en papel (origen) y una lista en el sistema (destino). MERGE revisa ambas y decide: si el empleado ya existe → actualiza sus datos; si es nuevo → lo agrega; si ya no aparece en el papel → lo elimina del sistema.
Idea clave: MERGE no es una operación nueva, sino una forma de escribir INSERT, UPDATE y DELETE juntos, decidiendo fila por fila cuál aplicar según si la fila está en el origen, en el destino o en ambos.

2. ¿Para qué sirve MERGE?

MERGE se utiliza principalmente para:

  • Sincronizar dos tablas que deben mantenerse iguales. // Sincronizar el inventario de una sucursal con el de la central.
  • Cargar datos desde un sistema externo (procesos ETL / importaciones). // Importar cada semana los clientes que llegan en un archivo Excel o CSV.
  • Hacer un upsert: “si existe, actualízalo; si no, créalo”. // Un formulario de la aplicación guarda un producto sin saber si ya existe.
  • Reemplazar combinaciones de INSERT + UPDATE + DELETE en un solo paso. // Evita escribir tres sentencias separadas con lógica IF EXISTS.
  • Mantener tablas de resumen o de totales cuando cambia el detalle. // Recalcular el resumen de ventas por producto al cerrar el día.

3. Las tres situaciones posibles

La clave para entender MERGE es visualizar qué puede pasar al comparar las filas del origen con las del destino usando la condición ON (normalmente la clave primaria):

ORIGEN (datos nuevos)
Solo en origen NOT MATCHED BY TARGET

→ INSERT
En ambas MATCHED

→ UPDATE (o DELETE)
Solo en destino NOT MATCHED BY SOURCE

→ DELETE (o UPDATE)
DESTINO (lo que hay en el sistema)
MATCHED

El registro existe en ambas tablas: el id aparece en origen y en destino. // Los datos del origen reemplazan a los del destino.
NOT MATCHED BY TARGET

El registro es nuevo: solo existe en origen. // Se agrega a la tabla destino.
NOT MATCHED BY SOURCE

El registro ya no existe en origen, pero sigue en destino. // Se elimina (o se marca como inactivo).
Para la clase: MERGE trabaja internamente como un FULL OUTER JOIN entre origen y destino. Cada fila del resultado cae en una de las tres zonas del diagrama, y según la zona se ejecuta la acción indicada. En el Paso 4 de la sección 6 lo veremos con una consulta.

4. Sintaxis de MERGE

La estructura siempre sigue el mismo patrón. Analicémosla parte por parte:

MERGE INTO TablaDestino AS destino            -- tabla que queremos actualizar
USING TablaOrigen AS origen                  -- tabla, vista, consulta o VALUES con los datos nuevos
ON destino.id = origen.id                     -- condición de coincidencia (clave de comparación)

WHEN MATCHED THEN                             -- existe en ambas → actualizar
    UPDATE SET destino.col = origen.col

WHEN NOT MATCHED BY TARGET THEN               -- existe en origen pero NO en destino → insertar
    INSERT (col1, col2) VALUES (origen.col1, origen.col2)

WHEN NOT MATCHED BY SOURCE THEN               -- existe en destino pero NO en origen → eliminar
    DELETE;                                      -- ¡el punto y coma final es OBLIGATORIO!
Cláusula ¿Qué pregunta? ¿Qué hace?
MERGE INTO … AS destino ¿Cuál es la tabla que quiero mantener actualizada? Declara la tabla destino y le da un alias corto. INTO es opcional.
USING … AS origen ¿De dónde vienen los datos nuevos? Declara la fuente: tabla, vista, tabla temporal, subconsulta o lista VALUES.
ON ¿Cómo sé si una fila del origen ya existe en el destino? Define la condición de comparación, normalmente por clave primaria.
WHEN MATCHED ¿La fila existe en ambas tablas? Ejecuta un UPDATE o un DELETE.
WHEN NOT MATCHED [BY TARGET] ¿La fila está en origen pero falta en destino? Ejecuta un INSERT. BY TARGET es opcional: es la opción por defecto.
WHEN NOT MATCHED BY SOURCE ¿La fila está en destino pero ya no está en origen? Ejecuta un DELETE o un UPDATE.
OUTPUT (opcional) ¿Qué hizo MERGE con cada fila? Devuelve las filas afectadas y la acción aplicada ($action). Ver sección 8.
Reglas que hay que conocer:
  • Las cláusulas WHEN son opcionales: usa solo las que necesites (mínimo una).
  • Cada WHEN puede llevar una condición extra con AND. // WHEN MATCHED AND destino.precio <> origen.precio THEN ...
  • Puede haber hasta dos WHEN MATCHED y hasta dos WHEN NOT MATCHED BY SOURCE: uno con UPDATE y otro con DELETE, y el primero debe llevar AND.
  • Solo puede haber un WHEN NOT MATCHED BY TARGET, y solo admite INSERT.
  • MERGE debe terminar con punto y coma (;). Sin él, SQL Server muestra el error 10713.

5. Ventajas y desventajas

Ventajas
  • Una sola pasada: lee origen y destino una vez y decide fila por fila, en lugar de recorrer las tablas tres veces (una por cada sentencia).
  • Atomicidad: al ser una única sentencia, las inserciones, actualizaciones y eliminaciones se aplican todas o ninguna, sin necesidad de abrir una transacción manual.
  • Legibilidad: expresa en un solo bloque la lógica de sincronización que de otra forma requeriría tres sentencias con IF EXISTS o NOT EXISTS.
  • Trazabilidad: con OUTPUT $action se obtiene, sin código adicional, qué se insertó, qué se actualizó y qué se eliminó.
Desventajas
  • Complejidad: la sintaxis es más extensa y un error en la condición ON o en NOT MATCHED BY SOURCE puede borrar muchas filas (ver sección 12).
  • Rendimiento en tablas grandes: sin índices en las columnas del ON, MERGE puede ser más lento que sentencias separadas bien optimizadas.
  • Concurrencia: si dos sesiones hacen el mismo upsert a la vez, ambas pueden intentar insertar la misma fila. Se evita con la sugerencia WITH (HOLDLOCK).
  • Errores conocidos: a lo largo de las versiones, Microsoft ha corregido varios errores de MERGE en escenarios avanzados (vistas indexadas, filtros, triggers). Conviene mantener SQL Server actualizado y probar bien antes de usarlo en producción.
  • Compatibilidad: la sintaxis varía entre motores. Oracle tiene MERGE pero sin BY SOURCE; PostgreSQL lo incorpora desde la versión 15; MySQL no tiene MERGE (usa INSERT ... ON DUPLICATE KEY UPDATE).

6. Base de datos de trabajo

Usaremos un escenario de inventario de una tienda con dos tablas: Inventario_Central (el destino: lo que tiene el sistema) e Inventario_Nuevo (el origen: la lista actualizada que llega cada semana). El objetivo de MERGE es dejar Inventario_Central igual a Inventario_Nuevo.

Paso 1 — Crear la base de datos

-- Crear solo si TiendaMERGE todavía no existe
IF DB_ID('TiendaMERGE') IS NULL
    CREATE DATABASE TiendaMERGE;
GO

USE TiendaMERGE;
GO
SELECT DB_NAME() AS base_actual;   -- debe mostrar TiendaMERGE
Antes de ejecutar: abre SSMS, conéctate al servidor y ejecuta los bloques en orden. No se elimina ninguna base existente: si TiendaMERGE ya existe, simplemente se usa.

Paso 2 — Crear las tablas

-- Si se repite la práctica, se recrean las tablas desde cero (solo dentro de TiendaMERGE)
DROP TABLE IF EXISTS Inventario_Central;
DROP TABLE IF EXISTS Inventario_Nuevo;
GO

-- Tabla DESTINO: lo que el sistema tiene registrado actualmente
CREATE TABLE Inventario_Central (
    id      INT PRIMARY KEY,                 -- PK manual (sin IDENTITY): el id lo trae el origen
    nombre  VARCHAR(100)   NOT NULL,
    precio  DECIMAL(10,2) NOT NULL,
    stock   INT NOT NULL DEFAULT 0,
    activo  BIT NOT NULL DEFAULT 1          -- 1 = activo, 0 = descontinuado (ejercicio 2)
);
GO

-- Tabla ORIGEN: la lista nueva que llega cada semana (archivo, otro sistema, etc.)
CREATE TABLE Inventario_Nuevo (
    id      INT PRIMARY KEY,
    nombre  VARCHAR(100)   NOT NULL,
    precio  DECIMAL(10,2) NOT NULL,
    stock   INT NOT NULL DEFAULT 0
);
GO

Paso 3 — Procedimiento para cargar (y reiniciar) los datos

Cada MERGE que ejecutemos modifica Inventario_Central; después del primero ya no quedarían diferencias. Por eso los datos se cargan con un procedimiento que podemos ejecutar antes de cada ejemplo para volver al estado inicial. 

CREATE OR ALTER PROCEDURE sp_reiniciar_datos
AS
BEGIN
    SET NOCOUNT ON;

    DELETE FROM Inventario_Central;   -- vaciar ambas tablas
    DELETE FROM Inventario_Nuevo;

    -- Estado actual del sistema (DESTINO)
    INSERT INTO Inventario_Central (id, nombre, precio, stock) VALUES
        (1,  'Teclado USB',             25.00, 50),   -- el precio cambiará
        (2,  'Mouse inalámbrico',       35.00, 30),   -- el stock cambiará
        (3,  'Monitor 24"',            320.00, 10),   -- sin cambios
        (4,  'Audífonos Bluetooth',     55.00, 20),   -- sin cambios
        (5,  'Webcam HD',               75.00, 15),   -- sin cambios
        (6,  'Micrófono USB',           48.00, 25),   -- sin cambios
        (7,  'Silla ergonómica',       190.00,  8),   -- será ELIMINADO: ya no está en la lista
        (8,  'Escritorio de pie',      250.00,  5),   -- será ELIMINADO: descontinuado
        (9,  'Lámpara LED escritorio',  22.00, 40),   -- precio y stock cambiarán
        (10, 'Hub USB 7 puertos',       18.00, 60);   -- sin cambios

    -- Lista nueva que llegó esta semana (ORIGEN)
    INSERT INTO Inventario_Nuevo (id, nombre, precio, stock) VALUES
        (1,  'Teclado USB',             29.00, 50),   -- precio subió de 25 a 29
        (2,  'Mouse inalámbrico',       35.00, 45),   -- stock reabastecido: 30 → 45
        (3,  'Monitor 24"',            320.00, 10),
        (4,  'Audífonos Bluetooth',     55.00, 20),
        (5,  'Webcam HD',               75.00, 15),
        (6,  'Micrófono USB',           48.00, 25),
        (9,  'Lámpara LED escritorio',  19.00, 55),   -- precio bajó y stock aumentó
        (10, 'Hub USB 7 puertos',       18.00, 60),
        (11, 'Disco SSD 1TB',           89.00, 12),   -- NUEVO
        (12, 'Memoria RAM 16GB',        45.00, 18),   -- NUEVO
        (13, 'Router WiFi 6',           65.00, 22);   -- NUEVO

    PRINT '✔ Datos reiniciados: Central = 10 filas, Nuevo = 11 filas.';
END;
GO

-- Cargar los datos por primera vez y revisarlos
EXEC sp_reiniciar_datos;
SELECT * FROM Inventario_Central ORDER BY id;
SELECT * FROM Inventario_Nuevo   ORDER BY id;
Rutina para cada ejemplo: ejecuta EXEC sp_reiniciar_datos;, luego el MERGE, y por último el SELECT de comprobación. El PRINT aparece en la pestaña Mensajes de SSMS y los SELECT en Resultados.

Paso 4 — Predecir qué hará MERGE (antes de ejecutarlo)

Esta consulta con FULL OUTER JOIN hace la misma comparación que MERGE, pero sin modificar nada. Es una excelente forma de revisar las diferencias antes de sincronizar. 

SELECT COALESCE(d.id, o.id)      AS id,
       d.precio AS precio_central,  o.precio AS precio_nuevo,
       d.stock  AS stock_central,   o.stock  AS stock_nuevo,
       CASE
           WHEN d.id IS NULL THEN 'INSERT'                     -- solo en origen
           WHEN o.id IS NULL THEN 'DELETE'                     -- solo en destino
           WHEN d.precio <> o.precio OR d.stock <> o.stock
                THEN 'UPDATE'                                 -- en ambas, con cambios
           ELSE 'sin cambios'                              -- en ambas, idénticas
       END AS accion_esperada
FROM Inventario_Central AS d
FULL OUTER JOIN Inventario_Nuevo AS o ON d.id = o.id
ORDER BY id;

7. El MERGE completo — las tres cláusulas

Con los datos cargados, ejecutamos MERGE para que Inventario_Central quede sincronizado con Inventario_Nuevo: 

EXEC sp_reiniciar_datos;   -- partir siempre del estado inicial
GO

-- MERGE completo: actualiza, inserta y elimina en un solo paso
MERGE INTO Inventario_Central AS destino        -- tabla que queremos actualizar
USING Inventario_Nuevo AS origen                -- tabla con los datos nuevos
ON destino.id = origen.id                       -- comparamos por id (clave primaria)

-- ① El id existe en ambas tablas → actualizar sus datos
WHEN MATCHED THEN
    UPDATE SET
        destino.nombre = origen.nombre,
        destino.precio = origen.precio,
        destino.stock  = origen.stock

-- ② El id está en origen pero no en destino → insertar como nuevo
WHEN NOT MATCHED BY TARGET THEN
    INSERT (id, nombre, precio, stock)
    VALUES (origen.id, origen.nombre, origen.precio, origen.stock)

-- ③ El id está en destino pero ya no aparece en origen → eliminar
WHEN NOT MATCHED BY SOURCE THEN
    DELETE;                                       -- punto y coma obligatorio
GO

-- Verificar el resultado final
SELECT * FROM Inventario_Central ORDER BY id;   -- ids 1–6 y 9–13 (7 y 8 eliminados)
Resultado esperado: Inventario_Central queda con 11 filas (ids 1–6 y 9–13). Los ids 7 y 8 desaparecieron, los ids 11, 12 y 13 se agregaron y los precios/stocks de 1, 2 y 9 se actualizaron.
Observa la pestaña Mensajes: dice (13 filas afectadas), no 8. Como WHEN MATCHED no tiene condición, MERGE también “actualizó” los ids 3, 4, 5, 6 y 10 aunque sus valores eran idénticos: 8 actualizaciones + 3 inserciones + 2 eliminaciones = 13. En la sección 9.2 veremos cómo evitarlo.

8. Ver qué hizo MERGE con OUTPUT

MERGE puede informar exactamente qué acción tomó con cada fila usando la cláusula OUTPUT. Dentro de ella están disponibles las mismas tablas especiales que en los triggers:

Elemento Contiene En un INSERT En un UPDATE En un DELETE
$action Texto con la acción aplicada 'INSERT' 'UPDATE' 'DELETE'
deleted.columna Valor anterior NULL valor antiguo valor eliminado
inserted.columna Valor nuevo valor insertado valor nuevo NULL

8.1 Mostrar las filas afectadas

EXEC sp_reiniciar_datos;
GO

MERGE INTO Inventario_Central AS destino
USING Inventario_Nuevo AS origen
ON destino.id = origen.id
WHEN MATCHED AND (destino.precio <> origen.precio OR destino.stock <> origen.stock) THEN
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock
WHEN NOT MATCHED BY TARGET THEN
    INSERT (id, nombre, precio, stock) VALUES (origen.id, origen.nombre, origen.precio, origen.stock)
WHEN NOT MATCHED BY SOURCE THEN
    DELETE

-- OUTPUT va al final, antes del punto y coma
OUTPUT
    $action                               AS accion,          -- 'INSERT', 'UPDATE' o 'DELETE'
    COALESCE(inserted.id, deleted.id)    AS id,              -- en un DELETE inserted.id es NULL
    deleted.precio                        AS precio_antes,    -- NULL si fue INSERT
    inserted.precio                       AS precio_despues,  -- NULL si fue DELETE
    deleted.stock                         AS stock_antes,
    inserted.stock                        AS stock_despues;
Resultado esperado: 8 filas: 3 UPDATE (ids 1, 2 y 9), 3 INSERT (ids 11, 12 y 13) y 2 DELETE (ids 7 y 8). Las eliminadas muestran solo los valores antes; las insertadas, solo los valores después; las actualizadas, ambos.

8.2 Guardar el resultado para ordenarlo y contarlo

OUTPUT no admite ORDER BY ni GROUP BY. Si queremos ordenar o resumir, guardamos las filas en una variable de tabla con OUTPUT ... INTO y luego la consultamos. 

EXEC sp_reiniciar_datos;
GO

-- Variable de tabla donde se guardará lo que hizo MERGE
DECLARE @cambios TABLE (
    accion         NVARCHAR(10),
    id             INT,
    precio_antes   DECIMAL(10,2),
    precio_despues DECIMAL(10,2)
);

MERGE INTO Inventario_Central AS destino
USING Inventario_Nuevo AS origen
ON destino.id = origen.id
WHEN MATCHED AND (destino.precio <> origen.precio OR destino.stock <> origen.stock) THEN
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock
WHEN NOT MATCHED BY TARGET THEN
    INSERT (id, nombre, precio, stock) VALUES (origen.id, origen.nombre, origen.precio, origen.stock)
WHEN NOT MATCHED BY SOURCE THEN
    DELETE
OUTPUT $action, COALESCE(inserted.id, deleted.id), deleted.precio, inserted.precio
INTO @cambios;                                     -- se guarda en lugar de mostrarse

-- Ahora sí podemos ordenar...
SELECT * FROM @cambios ORDER BY accion, id;

-- ...y resumir: DELETE = 2, INSERT = 3, UPDATE = 3
SELECT accion, COUNT(*) AS filas
FROM @cambios
GROUP BY accion;
Importante: la variable @cambios solo existe dentro del lote. Ejecuta desde DECLARE hasta el último SELECT juntos, sin un GO intermedio.

9. MERGE parcial y condicional

No siempre se necesitan las tres cláusulas, ni siempre deben aplicarse a todas las filas. MERGE es flexible: puedes usar solo las cláusulas que la situación requiera y agregarles condiciones.

9.1 Solo INSERT y UPDATE (sin eliminar)

Situación: Llega una lista de productos nuevos y actualizados, pero no queremos eliminar ninguno del sistema aunque ya no aparezca en la lista. 

EXEC sp_reiniciar_datos;
GO

MERGE INTO Inventario_Central AS destino
USING Inventario_Nuevo AS origen
ON destino.id = origen.id
WHEN MATCHED THEN                                            -- actualiza si ya existe
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock
WHEN NOT MATCHED BY TARGET THEN                              -- inserta si es nuevo
    INSERT (id, nombre, precio, stock) VALUES (origen.id, origen.nombre, origen.precio, origen.stock);
-- sin WHEN NOT MATCHED BY SOURCE → los registros que no están en el origen se conservan
GO

SELECT * FROM Inventario_Central ORDER BY id;   -- 13 filas: 7 y 8 siguen ahí

9.2 UPDATE solo cuando algo realmente cambió

Situación: Queremos evitar actualizar registros que no cambiaron, para no hacer escrituras innecesarias ni disparar triggers de auditoría con filas que no cambiaron. 

EXEC sp_reiniciar_datos;
GO

MERGE INTO Inventario_Central AS destino
USING Inventario_Nuevo AS origen
ON destino.id = origen.id
WHEN MATCHED AND                                             -- condición extra antes de actualizar
     (destino.precio <> origen.precio OR destino.stock <> origen.stock) THEN
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock
WHEN NOT MATCHED BY TARGET THEN
    INSERT (id, nombre, precio, stock) VALUES (origen.id, origen.nombre, origen.precio, origen.stock);
GO
-- Mensajes: (6 filas afectadas) → 3 UPDATE reales + 3 INSERT
Cuidado con los NULL: si alguna columna admite NULL, la comparación destino.col <> origen.col da “desconocido” cuando uno de los dos es NULL, y el cambio no se detecta. La forma segura de comparar varias columnas es con EXISTS ... EXCEPT, que trata dos NULL como iguales: 
WHEN MATCHED AND EXISTS (
         SELECT destino.precio, destino.stock      -- valores actuales
         EXCEPT
         SELECT origen.precio,  origen.stock       -- valores nuevos
     ) THEN                                      -- hay fila → algo es distinto
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock

9.3 Dos WHEN MATCHED: actualizar o eliminar según el dato

Situación: si en la lista nueva un producto llega con stock = 0, se considera agotado definitivamente y debe eliminarse; en cualquier otro caso se actualiza. 

EXEC sp_reiniciar_datos;
UPDATE Inventario_Nuevo SET stock = 0 WHERE id = 4;   -- simulamos que los audífonos se agotaron
GO

MERGE INTO Inventario_Central AS destino
USING Inventario_Nuevo AS origen
ON destino.id = origen.id
WHEN MATCHED AND origen.stock = 0 THEN                  -- ① primero el caso particular (con AND)
    DELETE
WHEN MATCHED THEN                                         -- ② después el caso general
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock
WHEN NOT MATCHED BY TARGET THEN
    INSERT (id, nombre, precio, stock) VALUES (origen.id, origen.nombre, origen.precio, origen.stock)
OUTPUT $action AS accion, COALESCE(inserted.id, deleted.id) AS id;
GO
-- El id 4 aparece como DELETE; 7 y 8 se conservan (no hay NOT MATCHED BY SOURCE)
El orden importa: SQL Server evalúa las cláusulas WHEN MATCHED en orden. La primera debe llevar AND; si fuera al revés, el caso general atraparía todas las filas y el DELETE nunca se ejecutaría (SQL Server, de hecho, no lo permite).

10. Otros orígenes de datos

El origen no tiene que ser una tabla. En USING puede ir cualquier conjunto de filas: una lista VALUES, una subconsulta, una tabla temporal, una vista o incluso parámetros.

10.1 Lista de valores con VALUES

EXEC sp_reiniciar_datos;
GO

MERGE INTO Inventario_Central AS destino
USING (VALUES                                              -- tabla "en línea"
        (2,  'Mouse inalámbrico', 33.00, 40),              -- existe → UPDATE
        (14, 'Parlantes 2.1',     70.00,  9)               -- no existe → INSERT
      ) AS origen (id, nombre, precio, stock)               -- nombres de las columnas
ON destino.id = origen.id
WHEN MATCHED THEN
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock
WHEN NOT MATCHED THEN                                     -- equivale a NOT MATCHED BY TARGET
    INSERT (id, nombre, precio, stock) VALUES (origen.id, origen.nombre, origen.precio, origen.stock);
GO

SELECT * FROM Inventario_Central WHERE id IN (2, 14);

10.2 Upsert desde un procedimiento almacenado

Situación: la aplicación tiene un botón “Guardar producto”. No sabe si el producto ya existe: si existe debe actualizarse, y si no, crearse. Es el caso de uso más común de MERGE. 

CREATE OR ALTER PROCEDURE sp_guardar_producto
    @id     INT,
    @nombre VARCHAR(100),
    @precio DECIMAL(10,2),
    @stock  INT
AS
BEGIN
    SET NOCOUNT ON;

    MERGE INTO Inventario_Central WITH (HOLDLOCK) AS destino   -- evita duplicados si dos usuarios guardan a la vez
    USING (SELECT @id AS id, @nombre AS nombre,
                  @precio AS precio, @stock AS stock) AS origen  -- una sola fila con los parámetros
    ON destino.id = origen.id
    WHEN MATCHED THEN
        UPDATE SET destino.nombre = origen.nombre,
                   destino.precio = origen.precio,
                   destino.stock  = origen.stock
    WHEN NOT MATCHED THEN
        INSERT (id, nombre, precio, stock)
        VALUES (origen.id, origen.nombre, origen.precio, origen.stock);
END;
GO

-- Prueba: la primera llamada inserta, la segunda actualiza
EXEC sp_guardar_producto 15, 'Tablet 10"', 299.00, 6;
EXEC sp_guardar_producto 15, 'Tablet 10"', 279.00, 6;   -- bajó el precio
SELECT * FROM Inventario_Central WHERE id = 15;           -- una sola fila, precio 279.00
¿Por qué HOLDLOCK? Sin él, dos sesiones podrían comprobar al mismo tiempo que el id 15 no existe y ambas intentarían insertarlo: una fallaría con error de clave primaria duplicada. HOLDLOCK bloquea el rango consultado hasta que termina el MERGE.

11. Auditoría con OUTPUT INTO una tabla

Combinando lo anterior, cada sincronización puede dejar un historial permanente de lo que cambió, quién lo hizo y cuándo, sin necesidad de triggers. 

-- Tabla de historial (se crea una sola vez)
DROP TABLE IF EXISTS HistorialMERGE;
CREATE TABLE HistorialMERGE (
    id_log         INT IDENTITY(1,1) PRIMARY KEY,
    accion         NVARCHAR(10),
    id_producto    INT,
    precio_antes   DECIMAL(10,2),
    precio_despues DECIMAL(10,2),
    stock_antes    INT,
    stock_despues  INT,
    usuario        VARCHAR(100) DEFAULT SYSTEM_USER,   -- quién ejecutó el MERGE
    fecha          DATETIME     DEFAULT GETDATE()     -- cuándo
);
GO

EXEC sp_reiniciar_datos;
GO

MERGE INTO Inventario_Central AS destino
USING Inventario_Nuevo AS origen
ON destino.id = origen.id
WHEN MATCHED AND (destino.precio <> origen.precio OR destino.stock <> origen.stock) THEN
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock
WHEN NOT MATCHED BY TARGET THEN
    INSERT (id, nombre, precio, stock) VALUES (origen.id, origen.nombre, origen.precio, origen.stock)
WHEN NOT MATCHED BY SOURCE THEN
    DELETE
OUTPUT $action, COALESCE(inserted.id, deleted.id),
       deleted.precio, inserted.precio, deleted.stock, inserted.stock
INTO HistorialMERGE (accion, id_producto, precio_antes, precio_despues, stock_antes, stock_despues);
GO

-- Revisar el historial persistente
SELECT * FROM HistorialMERGE ORDER BY id_log;
Resultado: HistorialMERGE guarda las 8 acciones con usuario y fecha. Como restricción, la tabla que recibe el OUTPUT INTO no puede tener triggers activos ni participar en claves foráneas.

12. Errores comunes y buenas prácticas

12.1 Olvidar el punto y coma

MERGE es una de las pocas sentencias de SQL Server que exige terminar en ;. Sin él se obtiene: Msg 10713: A MERGE statement must be terminated by a semi-colon (;).

// Revisa el final: ... WHEN NOT MATCHED BY SOURCE THEN DELETE; ← aquí

12.2 Filas repetidas en el origen

Si dos filas del origen coinciden con la misma fila del destino, MERGE no sabe cuál aplicar y cancela toda la operación. 

EXEC sp_reiniciar_datos;
GO

-- El id 1 llega DOS veces con precios distintos
MERGE INTO Inventario_Central AS destino
USING (VALUES (1, 30.00), (1, 31.00)) AS origen (id, precio)
ON destino.id = origen.id
WHEN MATCHED THEN
    UPDATE SET destino.precio = origen.precio;
-- Msg 8672: The MERGE statement attempted to UPDATE or DELETE the same row more than once.
GO

-- Solución: dejar una sola fila por id antes del MERGE (aquí, la de mayor precio)
WITH origen_unico AS (
    SELECT id, precio,
           ROW_NUMBER() OVER (PARTITION BY id ORDER BY precio DESC) AS rn
    FROM (VALUES (1, 30.00), (1, 31.00)) AS v (id, precio)
)
MERGE INTO Inventario_Central AS destino
USING (SELECT id, precio FROM origen_unico WHERE rn = 1) AS origen
ON destino.id = origen.id
WHEN MATCHED THEN
    UPDATE SET destino.precio = origen.precio;
GO

SELECT id, precio FROM Inventario_Central WHERE id = 1;   -- 31.00

12.3 NOT MATCHED BY SOURCE con un origen parcial

Es el error más peligroso. Si el origen trae solo una parte de los datos (por ejemplo, la lista de un solo proveedor), NOT MATCHED BY SOURCE considera que todo lo demás “desapareció” y lo elimina. 

EXEC sp_reiniciar_datos;
GO

-- Llega la lista actualizada SOLO del lote de productos 1 a 5
-- ✘ Si el destino fuera toda la tabla, se borrarían los ids 3 a 10 (¡8 productos!)
-- ✔ Solución: limitar el destino con una CTE al mismo lote que trae el origen
WITH destino_lote AS (
    SELECT * FROM Inventario_Central WHERE id BETWEEN 1 AND 5
)
MERGE INTO destino_lote AS destino
USING (VALUES (1, 29.00, 50), (2, 35.00, 45)) AS origen (id, precio, stock)
ON destino.id = origen.id
WHEN MATCHED THEN
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock
WHEN NOT MATCHED BY SOURCE THEN
    DELETE                                       -- solo borra 3, 4 y 5, que pertenecen al lote
OUTPUT $action AS accion, COALESCE(inserted.id, deleted.id) AS id;
GO

SELECT id, nombre FROM Inventario_Central ORDER BY id;   -- 1, 2 y 6–10 intactos
No filtres el destino en el ON: escribir ON destino.id = origen.id AND destino.id <= 5 parece lo mismo, pero no lo es: las filas del destino que no cumplen el filtro se consideran “sin coincidencia” y caen igual en NOT MATCHED BY SOURCE. El ON debe contener solo la comparación de claves; para limitar el destino usa una CTE (como arriba) o un AND en la cláusula WHEN.

12.4 Lista de buenas prácticas

Buena prácticaMotivo
Comparar solo por la clave en ON Evita inserciones y eliminaciones inesperadas (12.3).
Garantizar que el origen no tenga claves repetidas Evita el error 8672 (12.2). Usa DISTINCT, GROUP BY o ROW_NUMBER.
Agregar AND al WHEN MATCHED Solo se escriben las filas que cambiaron (9.2).
Usar WITH (HOLDLOCK) en upserts concurrentes Evita errores de clave duplicada cuando varios usuarios guardan a la vez (10.2).
Crear índices en las columnas del ON La comparación se resuelve mucho más rápido en tablas grandes.
Probar primero con FULL OUTER JOIN u OUTPUT dentro de una transacción Permite ver el efecto antes de confirmarlo (ROLLBACK si algo no cuadra).
Recordar que se disparan los triggers de la tabla destino Cada acción (INSERT, UPDATE, DELETE) dispara sus triggers AFTER, sin un orden garantizado entre ellas.

13. MERGE vs INSERT + UPDATE + DELETE por separado

Todo lo que hace MERGE puede escribirse con tres sentencias. Este es el equivalente exacto del MERGE de la sección 8.1, envuelto en una transacción para que también sea atómico: 

EXEC sp_reiniciar_datos;
GO

SET XACT_ABORT ON;          -- ante cualquier error, deshace toda la transacción
BEGIN TRANSACTION;

    -- ① UPDATE: filas en ambas tablas con cambios
    UPDATE destino
    SET destino.precio = origen.precio, destino.stock = origen.stock
    FROM Inventario_Central AS destino
    JOIN Inventario_Nuevo   AS origen ON destino.id = origen.id
    WHERE destino.precio <> origen.precio OR destino.stock <> origen.stock;

    -- ② INSERT: filas que solo están en el origen
    INSERT INTO Inventario_Central (id, nombre, precio, stock)
    SELECT o.id, o.nombre, o.precio, o.stock
    FROM Inventario_Nuevo AS o
    WHERE NOT EXISTS (SELECT 1 FROM Inventario_Central AS d WHERE d.id = o.id);

    -- ③ DELETE: filas que solo están en el destino
    DELETE d
    FROM Inventario_Central AS d
    WHERE NOT EXISTS (SELECT 1 FROM Inventario_Nuevo AS o WHERE o.id = d.id);

COMMIT;

SELECT * FROM Inventario_Central ORDER BY id;   -- mismo resultado que el MERGE: 11 filas
Criterio MERGE Sentencias separadas
Cantidad de código ✔ Un solo bloque Tres sentencias con JOIN / NOT EXISTS
Atomicidad ✔ Automática (una sentencia) Hay que usar BEGIN TRANSACTION manualmente
Lecturas de las tablas ✔ Una sola pasada Una por cada sentencia
Rendimiento en tablas muy grandes Depende mucho de los índices ✔ Cada sentencia se optimiza por separado
Facilidad de depuración Más difícil de aislar errores ✔ Se prueba cada operación
Reporte de cambios ✔ Nativo con OUTPUT $action Un OUTPUT distinto en cada sentencia
Portabilidad a otros motores Varía (MySQL no lo tiene) ✔ SQL estándar
Recomendación práctica: usa MERGE para sincronizar tablas, cargar datos externos o hacer upserts, cuando quieres resolverlo en un solo bloque y obtener el reporte con OUTPUT. Usa sentencias separadas cuando el volumen de datos es muy grande, cuando cada operación necesita lógica muy distinta o cuando el código debe funcionar en varios motores.

14. Resumen visual

Situación al comparar Cláusula WHEN Acciones permitidas Disponible en OUTPUT
id en origen y en destino WHEN MATCHED UPDATE o DELETE deleted (anterior) e inserted (nuevo)
id en origen, no en destino WHEN NOT MATCHED [BY TARGET] INSERT Solo inserted
id en destino, no en origen WHEN NOT MATCHED BY SOURCE DELETE o UPDATE Solo deleted (o ambas si es UPDATE)
Conexión con Triggers: cuando MERGE actúa sobre una tabla que tiene triggers, cada tipo de acción (INSERT, UPDATE, DELETE) dispara su trigger AFTER correspondiente, una vez por tipo de acción y con todas las filas afectadas. Las tablas inserted y deleted dentro de esos triggers funcionan exactamente igual que con sentencias separadas.
Las tres reglas de MERGE:
• En ON va solo la comparación de claves.
• El origen no debe traer claves repetidas.
• Termina siempre con punto y coma.

Cinco ejercicios para practicar MERGE. Los dos primeros usan la base de datos TiendaMERGE creada en la sección 6; los tres últimos usan la base de datos Northwind de Microsoft. Cada ejercicio incluye el enunciado, pistas y una solución oculta para revisar al final.

Recomendación: resuelve primero sin abrir la solución. Antes de cada ejercicio con TiendaMERGE ejecuta EXEC sp_reiniciar_datos;, y usa la consulta FULL OUTER JOIN del Paso 4 para predecir el resultado.

Ejercicio 1 — Sincronizar inventario sin eliminar descontinuados

Enunciado:

Usando Inventario_Central e Inventario_Nuevo, escribir un MERGE que:

  • Actualice precio y stock de los productos que ya existen, solo si cambiaron.
  • Inserte los productos nuevos.
  • No elimine ningún producto aunque no aparezca en la lista nueva.
  • Muestre con OUTPUT qué hizo con cada fila, con los precios antes y después.
Base de datos: TiendaMERGE
Pistas:
  • Omite la cláusula WHEN NOT MATCHED BY SOURCE para no eliminar.
  • Usa WHEN MATCHED AND (destino.precio <> origen.precio OR destino.stock <> origen.stock).
  • En OUTPUT: $action, deleted.precio e inserted.precio.
Ver solución 
EXEC sp_reiniciar_datos;
GO

MERGE INTO Inventario_Central AS destino
USING Inventario_Nuevo AS origen
ON destino.id = origen.id
WHEN MATCHED AND (destino.precio <> origen.precio OR destino.stock <> origen.stock) THEN
    UPDATE SET destino.precio = origen.precio, destino.stock = origen.stock
WHEN NOT MATCHED BY TARGET THEN
    INSERT (id, nombre, precio, stock) VALUES (origen.id, origen.nombre, origen.precio, origen.stock)
OUTPUT $action                            AS accion,
       COALESCE(inserted.id, deleted.id) AS id,
       deleted.precio                     AS precio_antes,
       inserted.precio                    AS precio_despues;
GO
-- OUTPUT: 3 UPDATE (1, 2, 9) y 3 INSERT (11, 12, 13)

SELECT * FROM Inventario_Central ORDER BY id;   -- 13 filas: 7 y 8 se conservan

Ejercicio 2 — Desactivar en vez de eliminar

Enunciado:

Modificar el MERGE completo (sección 7) para que, en vez de eliminar los productos que ya no están en la lista nueva, los marque como activo = 0.

  • Los productos que coinciden → actualizar precio y stock, y reactivarlos si estaban inactivos.
  • Los productos nuevos → insertar con activo = 1.
  • Los productos que ya no están en el origen → UPDATE SET activo = 0 en lugar de DELETE.
Base de datos: TiendaMERGE
Pistas:
  • En WHEN NOT MATCHED BY SOURCE se puede usar UPDATE en vez de DELETE.
  • Agrega AND destino.activo = 1 para no volver a “desactivar” uno que ya lo está.
  • Usa OUTPUT con deleted.activo e inserted.activo para verificar.
  • Ejecuta el MERGE dos veces: la segunda vez ya no debería desactivar nada.
Ver solución 
EXEC sp_reiniciar_datos;
GO

MERGE INTO Inventario_Central AS destino
USING Inventario_Nuevo AS origen
ON destino.id = origen.id
WHEN MATCHED THEN
    UPDATE SET destino.precio = origen.precio,
               destino.stock  = origen.stock,
               destino.activo = 1                         -- si volvió a la lista, se reactiva
WHEN NOT MATCHED BY TARGET THEN
    INSERT (id, nombre, precio, stock, activo)
    VALUES (origen.id, origen.nombre, origen.precio, origen.stock, 1)
WHEN NOT MATCHED BY SOURCE AND destino.activo = 1 THEN
    UPDATE SET destino.activo = 0                         -- baja lógica en lugar de DELETE
OUTPUT $action                            AS accion,
       COALESCE(inserted.id, deleted.id) AS id,
       deleted.activo                     AS activo_antes,
       inserted.activo                    AS activo_despues;
GO
-- Ningún DELETE: los ids 7 y 8 aparecen como UPDATE con activo 1 → 0

SELECT id, nombre, activo FROM Inventario_Central ORDER BY id;   -- 13 filas

Ejercicios con Northwind

Los siguientes 3 ejercicios usan la base de datos Northwind. Si no la tienes, descarga el script instnwnd.sql desde el repositorio oficial sql-server-samples de Microsoft en GitHub y ejecútalo en SSMS.

Tablas que usaremos:

  • Products — ProductID (IDENTITY), ProductName, UnitPrice, UnitsInStock, Discontinued, CategoryID, SupplierID
  • Categories — CategoryID (IDENTITY), CategoryName (NVARCHAR(15)), Description (NTEXT)
  • Customers — CustomerID (NCHAR(5)), CompanyName, ContactName, City, Country
Para no alterar Northwind: en las soluciones, el MERGE se ejecuta dentro de BEGIN TRANSACTION … ROLLBACK. Así se ve el resultado y luego todo vuelve a su estado original. Si quieres conservar los cambios, reemplaza ROLLBACK por COMMIT.

Ejercicio 3 — Sincronizar la lista de precios de productos

Enunciado:

El departamento de compras envía una lista de precios. Crear una tabla temporal #ListaPrecios y usar MERGE sobre Products para:

  • Si el producto ya existe → actualizar UnitPrice solo si el precio cambió.
  • Si el producto es nuevo → insertarlo.
  • No eliminar ningún producto que no esté en la lista.
  • Mostrar con OUTPUT qué productos se actualizaron y cuáles se insertaron.
Base de datos: Northwind
Pistas:
  • ProductID es IDENTITY: en el INSERT no se incluye; SQL Server lo genera.
  • Para los productos nuevos, deja ProductID en NULL en #ListaPrecios: NULL nunca coincide en el ON, así que caen en NOT MATCHED BY TARGET.
  • Crea la tabla temporal antes del BEGIN TRANSACTION (el ROLLBACK la eliminaría).
  • Precios originales: Chai (1) = 18.00, Chang (2) = 19.00, Aniseed Syrup (3) = 10.00.
Ver solución 
USE Northwind;
GO

DROP TABLE IF EXISTS #ListaPrecios;
CREATE TABLE #ListaPrecios (
    ProductID   INT NULL,                 -- NULL = producto nuevo
    ProductName NVARCHAR(40) NOT NULL,
    UnitPrice   MONEY NOT NULL,
    CategoryID  INT,
    SupplierID  INT
);
INSERT INTO #ListaPrecios VALUES
    (1,    N'Chai',           20.00, 1, 1),   -- 18.00 → 20.00 (UPDATE)
    (2,    N'Chang',          19.00, 1, 1),   -- igual (no se toca)
    (3,    N'Aniseed Syrup',  12.50, 2, 1),   -- 10.00 → 12.50 (UPDATE)
    (NULL, N'Café de Altura', 25.00, 1, 1);   -- nuevo (INSERT)
GO

BEGIN TRANSACTION;

MERGE INTO Products AS destino
USING #ListaPrecios AS origen
ON destino.ProductID = origen.ProductID
WHEN MATCHED AND destino.UnitPrice <> origen.UnitPrice THEN
    UPDATE SET destino.UnitPrice = origen.UnitPrice
WHEN NOT MATCHED BY TARGET THEN
    INSERT (ProductName, UnitPrice, CategoryID, SupplierID, Discontinued)   -- sin ProductID
    VALUES (origen.ProductName, origen.UnitPrice, origen.CategoryID, origen.SupplierID, 0)
OUTPUT $action            AS accion,
       inserted.ProductID  AS ProductID,          -- id generado (78 la primera vez; el ROLLBACK no reinicia el IDENTITY)
       inserted.ProductName,
       deleted.UnitPrice   AS precio_antes,
       inserted.UnitPrice  AS precio_despues;

SELECT ProductID, ProductName, UnitPrice
FROM Products
WHERE ProductID IN (1, 2, 3) OR ProductName = N'Café de Altura';

ROLLBACK;   -- deshace los cambios en Northwind

Ejercicio 4 — Actualizar el catálogo de categorías

Enunciado:

La empresa reorganiza sus categorías. Crear una tabla temporal #CategoriasNuevas con el catálogo actualizado y usar MERGE sobre Categories para:

  • Actualizar la Description de las categorías existentes si cambió.
  • Insertar categorías nuevas (por ejemplo, “Tecnología” e “Higiene”).
  • Eliminar las categorías que no aparecen en el catálogo solo si no tienen productos asociados.
  • Mostrar con OUTPUT cada acción tomada.
Base de datos: Northwind
Pistas:
  • Description es NTEXT y no se puede comparar con <>: conviértela con CAST(destino.Description AS NVARCHAR(MAX)).
  • Para eliminar solo categorías sin productos: WHEN NOT MATCHED BY SOURCE AND NOT EXISTS (SELECT 1 FROM Products p WHERE p.CategoryID = destino.CategoryID).
  • Las 8 categorías originales tienen productos, así que ninguna se eliminará. Para comprobar el DELETE, inserta antes una categoría de prueba vacía dentro de la transacción.
  • CategoryName admite máximo 15 caracteres.
Ver solución 
USE Northwind;
GO

DROP TABLE IF EXISTS #CategoriasNuevas;
CREATE TABLE #CategoriasNuevas (
    CategoryID   INT NULL,                -- NULL = categoría nueva
    CategoryName NVARCHAR(15) NOT NULL,
    Description  NVARCHAR(MAX)
);
INSERT INTO #CategoriasNuevas VALUES
    (1,    N'Beverages',  N'Bebidas: gaseosas, café, té y cervezas'),    -- cambia la descripción
    (2,    N'Condiments', N'Salsas, condimentos y especias'),           -- cambia la descripción
    (NULL, N'Tecnología', N'Accesorios y productos electrónicos'),     -- nueva
    (NULL, N'Higiene',    N'Cuidado personal');                       -- nueva
GO

BEGIN TRANSACTION;

-- Categoría de prueba SIN productos: debe eliminarse
INSERT INTO Categories (CategoryName, Description) VALUES (N'Temporal', N'Sin productos');

MERGE INTO Categories AS destino
USING #CategoriasNuevas AS origen
ON destino.CategoryID = origen.CategoryID
WHEN MATCHED AND ISNULL(CAST(destino.Description AS NVARCHAR(MAX)), N'')
              <> ISNULL(origen.Description, N'') THEN                -- NTEXT → NVARCHAR(MAX)
    UPDATE SET destino.Description = origen.Description
WHEN NOT MATCHED BY TARGET THEN
    INSERT (CategoryName, Description) VALUES (origen.CategoryName, origen.Description)
WHEN NOT MATCHED BY SOURCE
     AND NOT EXISTS (SELECT 1 FROM Products AS p WHERE p.CategoryID = destino.CategoryID) THEN
    DELETE                                                        -- solo categorías vacías
OUTPUT $action                                              AS accion,
       COALESCE(inserted.CategoryID, deleted.CategoryID)     AS CategoryID,
       COALESCE(inserted.CategoryName, deleted.CategoryName) AS CategoryName;
-- Esperado: UPDATE 1 y 2 · INSERT Tecnología e Higiene · DELETE Temporal · 3–8 intactas

SELECT CategoryID, CategoryName, CAST(Description AS NVARCHAR(200)) AS Description
FROM Categories ORDER BY CategoryID;

ROLLBACK;

Ejercicio 5 — Sincronizar el directorio de clientes

Enunciado:

La empresa recibe un archivo CSV con el directorio actualizado de clientes. Simularlo con una tabla temporal #ClientesActualizados y usar MERGE sobre Customers para:

  • Actualizar ContactName, City y Country si alguno cambió (considerando que pueden ser NULL).
  • Insertar clientes completamente nuevos.
  • No eliminar clientes existentes.
  • Generar un reporte con OUTPUT: acción, CustomerID y los valores anteriores y nuevos de ContactName y City.
Base de datos: Northwind
Pistas:
  • CustomerID es NCHAR(5), no un entero. Ej: 'ALFKI'.
  • Para comparar tres columnas que admiten NULL, usa el patrón EXISTS (SELECT ... EXCEPT SELECT ...) de la sección 9.2.
  • Inventa un CustomerID de 5 caracteres para el cliente nuevo (ej: 'VENZL').
  • CompanyName es NOT NULL: no olvides incluirlo en el INSERT.
Ver solución 
USE Northwind;
GO

DROP TABLE IF EXISTS #ClientesActualizados;
CREATE TABLE #ClientesActualizados (
    CustomerID  NCHAR(5) PRIMARY KEY,         -- la PK impide claves repetidas en el origen
    CompanyName NVARCHAR(40) NOT NULL,
    ContactName NVARCHAR(30),
    City        NVARCHAR(15),
    Country     NVARCHAR(15)
);
INSERT INTO #ClientesActualizados VALUES
    (N'ALFKI', N'Alfreds Futterkiste',     N'Maria Anders',  N'Hamburg', N'Germany'),    -- cambió City
    (N'ANTON', N'Antonio Moreno Taquería', N'Juan Moreno',   N'México D.F.', N'Mexico'), -- cambió ContactName
    (N'VENZL', N'Arepas del Ávila',        N'Carla Rivas',   N'Caracas', N'Venezuela');  -- nuevo
GO

BEGIN TRANSACTION;

MERGE INTO Customers AS destino
USING #ClientesActualizados AS origen
ON destino.CustomerID = origen.CustomerID
WHEN MATCHED AND EXISTS (
         SELECT destino.ContactName, destino.City, destino.Country
         EXCEPT
         SELECT origen.ContactName,  origen.City,  origen.Country
     ) THEN                                               -- detecta cambios aunque haya NULL
    UPDATE SET destino.ContactName = origen.ContactName,
               destino.City        = origen.City,
               destino.Country     = origen.Country
WHEN NOT MATCHED BY TARGET THEN
    INSERT (CustomerID, CompanyName, ContactName, City, Country)
    VALUES (origen.CustomerID, origen.CompanyName, origen.ContactName, origen.City, origen.Country)
OUTPUT $action                                      AS accion,
       COALESCE(inserted.CustomerID, deleted.CustomerID) AS CustomerID,
       deleted.ContactName  AS contacto_antes,  inserted.ContactName AS contacto_despues,
       deleted.City         AS ciudad_antes,    inserted.City        AS ciudad_despues;
-- Esperado: UPDATE ALFKI (Berlin → Hamburg) · UPDATE ANTON (Antonio → Juan) · INSERT VENZL

ROLLBACK;
