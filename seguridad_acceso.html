1. ¿Qué es la seguridad de base de datos?

La seguridad de base de datos es una parte esencial de la administración de bases de datos, especialmente en entornos empresariales donde la integridad y la confidencialidad de la información son prioritarias.

En SQL Server se implementa mediante un sistema que abarca la gestión de usuarios, roles, permisos y la auditoría de eventos.

Dicho de forma simple, la seguridad responde tres preguntas cada vez que alguien intenta trabajar con los datos: ¿quién eres?, ¿qué puedes hacer? y ¿qué hiciste?

Idea clave: En SQL Server nadie tiene acceso a nada por defecto. Todo acceso debe concederse explícitamente, y lo recomendable es conceder solo lo mínimo necesario (principio de mínimo privilegio).

2. Los cuatro pilares de la seguridad

Pilar Pregunta que responde Herramienta en SQL Server
Autenticación ¿Quién eres? Logins (Windows o SQL Server), contraseñas y sus políticas. // CREATE LOGIN LoginFinanciera WITH PASSWORD = '...';
Autorización ¿Qué puedes hacer? Usuarios, roles y permisos. // GRANT SELECT ON dbo.CLIENTE TO UsuarioBDFinanciera;
Auditoría ¿Qué hiciste y cuándo? SQL Server Audit (auditorías de servidor y de base de datos). // CREATE SERVER AUDIT AuditoriaInicioSesion ...
Protección de datos ¿Y si alguien ve lo que no debe? Enmascaramiento dinámico, Always Encrypted, cifrado de columnas. // ALTER TABLE ... ADD MASKED WITH (FUNCTION = 'email()');

3. Entidades de seguridad (principals)

Una entidad de seguridad (en inglés principal) es alguien que puede solicitar acceso a los recursos de SQL Server: una persona, un grupo o una aplicación. Existen en tres niveles:

Nivel Entidades de seguridad Ejemplo
Windows Cuenta de usuario local de Windows
Cuenta de usuario de dominio
Grupo de Windows		 MIPC\Alumno, UCV\jperez, UCV\Docentes
Servidor SQL Server Inicio de sesión (login) de SQL Server
Rol de servidor		 LoginFinanciera, sysadmin
Base de datos Usuario de base de datos
Rol de base de datos
Rol de aplicación		 UsuarioBDFinanciera, db_datareader

4. Asegurables (securables)

Los asegurables son los recursos a los cuales el sistema de autorización controla el acceso. Están organizados como cajas dentro de cajas: un permiso dado en una caja exterior suele aplicarse a todo lo que contiene.

Servidor
Logins · Roles de servidor · Bases de datos · Endpoints (HTTP)
Base de datos
Usuarios · Roles · Roles de aplicación · Certificados · Assemblies · Esquemas
Esquema (por ejemplo dbo)
Objetos
Tablas · Vistas · Funciones · Procedimientos almacenados · Reglas · Defaults
Ejemplo de herencia: si se concede SELECT sobre el esquema dbo, el usuario podrá leer todas las tablas y vistas de ese esquema, incluso las que se creen después. // GRANT SELECT ON SCHEMA::dbo TO UsuarioBDFinanciera;

5. Modos de autenticación

Autenticar significa comprobar la identidad de quien se conecta. SQL Server ofrece dos formas de hacerlo:

Autenticación de Windows — Windows confirma la identidad.

Cuando un usuario se conecta con una cuenta de Windows, SQL Server valida el nombre de cuenta y la contraseña con el token de seguridad del sistema operativo. SQL Server no pide la contraseña ni realiza la validación de identidad.

  • Es el modo predeterminado y es más seguro.
  • Usa el protocolo Kerberos.
  • Aplica las directivas de contraseña de Windows: complejidad, bloqueo de cuentas y expiración.
  • Se le llama conexión de confianza (trusted connection).
  • Permite crear un único login para un grupo de Windows completo. // CREATE LOGIN [UCV\Docentes] FROM WINDOWS; → todos los docentes del grupo acceden
Analogía: Es como entrar a la universidad mostrando el carné que ya te revisaron en la puerta principal. El guardia del aula confía en que la puerta principal ya verificó quién eres.

Autenticación de SQL Server — SQL Server guarda y valida las credenciales.

Los inicios de sesión se crean en SQL Server y no dependen de cuentas de Windows. El nombre de usuario y la contraseña se almacenan en SQL Server.

  • El usuario debe escribir su login y contraseña cada vez que se conecta.
  • Hay que establecer contraseñas seguras para todas las cuentas.
  • Útil para aplicaciones web, equipos fuera del dominio o sistemas Linux.
  • SQL Server crea una cuenta de administrador llamada sa, con privilegios completos.
Analogía: Es como un aula con candado de clave propia: no importa quién seas afuera, dentro solo vale la clave que el aula conoce.
Característica Windows SQL Server
¿Quién valida la contraseña? Windows / Active Directory SQL Server
¿Pide contraseña al conectar? No (usa la sesión de Windows) Sí, cada vez
Políticas de contraseña Las del dominio Opcionales (CHECK_POLICY)
Nivel de seguridad Mayor Menor (las credenciales viajan desde la aplicación)
Uso típico Redes corporativas con dominio Aplicaciones web, servicios externos
Antes de la práctica — habilitar el modo mixto: para poder conectarse con un login de SQL Server, el servidor debe aceptar ambos modos. En SSMS: clic derecho sobre el servidor → Propiedades → Seguridad → marcar Modo de autenticación de SQL Server y de Windows → Aceptar. Luego reiniciar el servicio de SQL Server (clic derecho sobre el servidor → Reiniciar). 
-- Comprobar el modo de autenticación actual del servidor
SELECT CASE SERVERPROPERTY('IsIntegratedSecurityOnly')
         WHEN 1 THEN 'Solo Windows'
         ELSE 'Mixto: Windows y SQL Server'   -- necesario para la práctica
       END AS modo_autenticacion;
Sobre la cuenta sa: nunca debe usarse para conectar aplicaciones. Es buena práctica asignarle una contraseña muy fuerte, o directamente deshabilitarla. // ALTER LOGIN sa DISABLE;

“Puedes abrir este archivador”

-- 1) El login permite conectarse al SERVIDOR
CREATE LOGIN UsuarioEjemplo WITH PASSWORD = 'ContraseñaSegura#1';

-- 2) El usuario permite entrar a UNA base de datos (se crea estando dentro de ella)
CREATE USER UsuarioEjemplo FOR LOGIN UsuarioEjemplo;
Regla de oro: un login sin usuario puede conectarse al servidor, pero no puede abrir ninguna base de datos (salvo las del sistema). Un usuario sin permisos puede entrar a la base de datos, pero no puede leer ni modificar ninguna tabla.

7. Roles

Los roles agrupan entidades de seguridad para administrar permisos con facilidad. Son como los grupos de Windows: en lugar de dar el mismo permiso a 30 usuarios uno por uno, se le da al rol y se agrega a los 30 usuarios al rol.

7.1 Roles fijos de servidor

Su alcance es todo el servidor. Se asignan a logins.

Rol¿Qué pueden hacer sus miembros?
sysadminCualquier actividad en el servidor. Es el máximo privilegio.
serveradminCambiar opciones de configuración y apagar el servidor.
securityadminAdministrar logins y sus permisos. Puede elevar privilegios: supervisar.
processadminFinalizar procesos que se ejecutan en el servidor.
setupadminAgregar y quitar servidores vinculados.
bulkadminEjecutar la instrucción BULK INSERT.
diskadminAdministrar archivos de disco.
dbcreatorCrear, modificar, eliminar y restaurar cualquier base de datos.
publicTodo login pertenece a public. Sus permisos los heredan todos.

7.2 Roles fijos de base de datos

Su alcance es una base de datos. Se asignan a usuarios.

Rol¿Qué pueden hacer sus miembros?
db_owner Todas las actividades de configuración y mantenimiento, incluso eliminar la base de datos.
db_securityadmin Modificar la pertenencia a roles personalizados y administrar permisos. Pueden elevar sus privilegios: se deben supervisar sus acciones.
db_accessadmin Agregar o quitar acceso a la base de datos para logins y grupos de Windows y de SQL Server.
db_backupoperator Crear copias de seguridad de la base de datos.
db_ddladmin Ejecutar cualquier comando DDL (CREATE, ALTER, DROP).
db_datawriter Agregar, eliminar o cambiar datos en todas las tablas de usuario.
db_datareader Leer todos los datos de todas las tablas y vistas de usuario (en cualquier esquema excepto sys e INFORMATION_SCHEMA).
db_denydatawriter No pueden agregar, modificar ni eliminar datos de tablas de usuario.
db_denydatareader No pueden leer datos de tablas ni vistas de usuario.
public Todo usuario pertenece a public. Conviene no concederle permisos.
Para recordar: los roles db_deny... existen para bloquear. Si un usuario está en db_datareader y en db_denydatareader al mismo tiempo, no puede leer: la denegación siempre gana (ver sección 8).

7.3 El usuario dbo no es lo mismo que el rol db_owner

  • dbo (database owner) es una cuenta de usuario con permisos implícitos para hacer todo en la base de datos. Los miembros del rol de servidor sysadmin se asignan automáticamente a dbo.
  • db_owner es un rol. Ser miembro de db_owner no convierte a nadie en el usuario dbo.
  • El alcance de db_owner es una base de datos; el de sysadmin es todo el servidor.
// SELECT USER_NAME(); → si estás conectado como sysadmin, devuelve 'dbo'

7.4 Roles personalizados

Además de los roles fijos, se pueden crear roles propios que reflejen los puestos de la organización (vendedor, cajero, auditor...). Es la forma recomendada de dar permisos. 

-- Crear el rol (dentro de la base de datos)
CREATE ROLE RolEjemplo;

-- Dar permisos AL ROL, no a cada usuario
GRANT SELECT ON dbo.CLIENTE TO RolEjemplo;

-- Agregar un usuario al rol (sintaxis actual)
ALTER ROLE RolEjemplo ADD MEMBER UsuarioEjemplo;

-- Sintaxis antigua, equivalente (seguirás viéndola en material y scripts heredados)
EXEC sp_addrolemember 'RolEjemplo', 'UsuarioEjemplo';
Sintaxis antigua vs actual: sp_addrolemember y sp_addsrvrolemember siguen funcionando, pero Microsoft los marca como obsoletos. En código nuevo usa ALTER ROLE ... ADD MEMBER y ALTER SERVER ROLE ... ADD MEMBER.

8. Permisos: GRANT, DENY y REVOKE

Un permiso es la autorización para realizar una acción concreta sobre un asegurable. Se administran con tres instrucciones:

Instrucción ¿Qué hace? Ejemplo
GRANT Concede el permiso. GRANT SELECT ON dbo.CLIENTE TO UsuarioEjemplo;
DENY Prohíbe el permiso de forma explícita, aunque un rol lo conceda. DENY DELETE ON dbo.CLIENTE TO UsuarioEjemplo;
REVOKE Quita un GRANT o un DENY dado antes. Vuelve al estado neutral. REVOKE DELETE ON dbo.CLIENTE FROM UsuarioEjemplo;
Regla de precedencia: DENY siempre gana

Si un usuario recibe GRANT SELECT por un rol y DENY SELECT por otro lado, no podrá leer. En cambio, REVOKE no prohíbe nada: solo borra lo que se había concedido o denegado, y el usuario puede seguir teniendo el permiso a través de un rol.

Analogía: GRANT es darle una llave, DENY es ponerle su nombre en la lista negra del guardia (aunque tenga llave, no entra) y REVOKE es quitarle la llave o borrarlo de la lista negra.

9. Práctica paso a paso

Vamos a construir la base de datos FinancieraDemoBD y sobre ella crear logins, usuarios, roles y permisos. Ejecuta los bloques en orden en SSMS, conectado con una cuenta administradora (la tuya de Windows o sa).

¿Cómo probamos sin desconectarnos? Con EXECUTE AS USER = '...' SQL Server ejecuta las siguientes instrucciones como si fueras ese usuario. Con REVERT vuelves a ser tú. Así comprobamos cada permiso en la misma ventana.

Paso 1 — Crear la base de datos y sus tablas

-- Crear solo si FinancieraDemoBD todavía no existe
CREATE DATABASE FinancieraDemoBD;
GO

USE FinancieraDemoBD;
GO

-- ① CLIENTE: datos de contacto (algunos serán sensibles: email, teléfono)
CREATE TABLE CLIENTE (
    id_cliente  INT IDENTITY(1,1) PRIMARY KEY,
    nombre      VARCHAR(100) NOT NULL,
    documento   VARCHAR(15)  NOT NULL,
    email       VARCHAR(150),
    telefono    VARCHAR(20)
);
GO

-- ② PROVEEDOR: empresas que abastecen a la financiera
CREATE TABLE PROVEEDOR (
    id_proveedor INT IDENTITY(1,1) PRIMARY KEY,
    razon_social VARCHAR(150) NOT NULL,
    ruc          VARCHAR(15)  NOT NULL,

);
GO

-- ③ COLABORADOR: empleados; el sueldo es un dato confidencial
CREATE TABLE COLABORADOR (

Paso 3 — Crear el login (nivel servidor)

Los logins se crean desde la base master. Verificamos primero que no exista para que el script pueda ejecutarse más de una vez sin error. 

USE master;
GO

-- Crear el login solo si todavía no existe
IF NOT EXISTS (SELECT name FROM sys.server_principals WHERE name = N'LoginFinanciera')
    CREATE LOGIN [LoginFinanciera]
    WITH PASSWORD = N'Protect2020',                -- contraseña (N = texto Unicode)
         DEFAULT_DATABASE = [FinancieraDemoBD],   -- base que se abre al conectarse
         CHECK_POLICY = ON;                      -- exige las reglas de complejidad de Windows
GO

-- Comprobación: el login aparece como SQL_LOGIN
SELECT name, type_desc, default_database_name, create_date
FROM sys.server_principals
WHERE name = 'LoginFinanciera';
Otras formas de crear logins:
  • Login de Windows: el nombre debe ser DOMINIO\usuario o EQUIPO\usuario, y no lleva contraseña. // CREATE LOGIN [MIPC\Alumno] FROM WINDOWS WITH DEFAULT_DATABASE = [FinancieraDemoBD];
  • Asignar un rol de servidor al login (con mucho cuidado: dbcreator permite crear y borrar bases de datos). // ALTER SERVER ROLE dbcreator ADD MEMBER [LoginFinanciera]; // Sintaxis antigua: EXEC sp_addsrvrolemember 'LoginFinanciera', 'dbcreator';

Paso 4 — Crear el usuario de base de datos

USE FinancieraDemoBD;   -- el usuario se crea DENTRO de la base de datos
GO

IF NOT EXISTS (SELECT name FROM sys.database_principals WHERE name = N'UsuarioBDFinanciera')
    CREATE USER [UsuarioBDFinanciera] FOR LOGIN [LoginFinanciera];   -- enlaza usuario ↔ login
GO

-- Prueba: todavía NO tiene permisos sobre las tablas
EXECUTE AS USER = 'UsuarioBDFinanciera';
    SELECT USER_NAME() AS usuario_actual;      -- UsuarioBDFinanciera
    SELECT * FROM CLIENTE;                      -- ERROR 229: permiso SELECT denegado
REVERT;
Resultado esperado: el primer SELECT muestra el nombre del usuario y el segundo falla con el error 229 (permiso denegado). Es correcto: el usuario existe, pero aún no se le ha concedido nada. Si un error interrumpe el lote antes del REVERT, ejecuta REVERT; por separado.

Paso 5 — Asignar roles y conceder permisos

USE FinancieraDemoBD;
GO

-- ① Roles fijos: leer y escribir en TODAS las tablas
ALTER ROLE db_datareader ADD MEMBER [UsuarioBDFinanciera];
ALTER ROLE db_datawriter ADD MEMBER [UsuarioBDFinanciera];
-- Equivalente antiguo: EXEC sp_addrolemember N'db_datareader', N'UsuarioBDFinanciera';
GO

-- ② EXECUTE sin objeto: permite ejecutar TODOS los procedimientos de la base
GRANT EXECUTE TO [UsuarioBDFinanciera];

-- ③ O bien, permisos objeto por objeto (más controlado)
GRANT EXECUTE ON spListar_Clientes    TO [UsuarioBDFinanciera];
GRANT EXECUTE ON spInsertar_Cliente   TO [UsuarioBDFinanciera];
GRANT EXECUTE ON spListar_Proveedor   TO [UsuarioBDFinanciera];
GRANT EXECUTE ON spInsertar_Proveedor TO [UsuarioBDFinanciera];
GRANT SELECT, INSERT, UPDATE, DELETE ON dbo.CLIENTE     TO [UsuarioBDFinanciera];
GRANT SELECT, INSERT, UPDATE, DELETE ON dbo.PROVEEDOR   TO [UsuarioBDFinanciera];
GRANT SELECT, INSERT, UPDATE, DELETE ON dbo.COLABORADOR TO [UsuarioBDFinanciera];

-- ④ Permiso especial: ALTER permite cambiar la ESTRUCTURA de la tabla → evaluar riesgos
GRANT ALTER ON dbo.CLIENTE TO [UsuarioBDFinanciera];
GO

-- Prueba: ahora sí puede leer y ejecutar
EXECUTE AS USER = 'UsuarioBDFinanciera';
    SELECT * FROM CLIENTE;               -- OK
    EXEC spListar_Proveedor;             -- OK
REVERT;
Atención: en este paso se muestran a propósito varias formas de dar permisos, y el usuario termina con mucho más de lo necesario (roles + permisos explícitos + ALTER). En un sistema real se elige una sola estrategia y se concede lo mínimo. El siguiente paso muestra la forma recomendada.

Paso 6 — Mínimo privilegio: acceso solo a través de procedimientos

Un patrón muy usado en aplicaciones: el usuario de la aplicación no puede tocar las tablas directamente; solo puede ejecutar procedimientos. Así la aplicación nunca ve columnas que no necesita. 

USE FinancieraDemoBD;
GO

-- Usuario SIN login: no puede conectarse, pero sirve para probar permisos en clase
CREATE USER UsuarioApp WITHOUT LOGIN;

-- Solo puede ejecutar el procedimiento de listado
GRANT EXECUTE ON spListar_Clientes TO UsuarioApp;
GO

EXECUTE AS USER = 'UsuarioApp';
    EXEC spListar_Clientes;     -- OK: devuelve id, nombre y email
REVERT;

EXECUTE AS USER = 'UsuarioApp';
    SELECT * FROM CLIENTE;      -- ERROR 229: no tiene SELECT sobre la tabla
REVERT;
¿Por qué funciona el procedimiento si no tiene SELECT sobre la tabla? Por el encadenamiento de propiedad (ownership chaining): el procedimiento y la tabla tienen el mismo dueño (dbo), así que SQL Server solo verifica el permiso EXECUTE sobre el procedimiento. Esto convierte a los procedimientos en una capa de seguridad.

Paso 7 — DENY y REVOKE en acción

UsuarioBDFinanciera puede leer COLABORADOR (por db_datareader y por el GRANT del paso 5). Vamos a bloquearlo y después a deshacer el bloqueo. 

-- ① DENY: aunque los roles lo permitan, la denegación gana
DENY SELECT ON dbo.COLABORADOR TO [UsuarioBDFinanciera];
GO

EXECUTE AS USER = 'UsuarioBDFinanciera';
    SELECT * FROM COLABORADOR;   -- ERROR 229: DENY tiene prioridad sobre db_datareader
REVERT;
GO

-- ② REVOKE: borra el DENY (y también el GRANT explícito del paso 5)
REVOKE SELECT ON dbo.COLABORADOR FROM [UsuarioBDFinanciera];
GO

EXECUTE AS USER = 'UsuarioBDFinanciera';
    SELECT * FROM COLABORADOR;   -- OK otra vez: lo sigue permitiendo db_datareader
REVERT;
Resultado: después del REVOKE el usuario vuelve a leer la tabla, aunque ya no tenga ningún permiso explícito sobre ella. Esto demuestra que REVOKE no equivale a prohibir: el permiso sigue llegando a través del rol.

Paso 8 — Rol personalizado con permisos por columna

Recursos Humanos necesita ver el sueldo; el área comercial solo necesita el nombre y el cargo. Creamos un rol para cada caso. 

USE FinancieraDemoBD;
GO

-- Rol comercial: clientes completos, colaboradores SIN sueldo
CREATE ROLE RolVendedor;
GRANT SELECT, INSERT ON dbo.CLIENTE TO RolVendedor;
GRANT SELECT ON dbo.COLABORADOR (id_colaborador, nombre, cargo) TO RolVendedor;   -- permiso por columnas

-- Rol de RR.HH.: todo sobre COLABORADOR
CREATE ROLE RolRRHH;
GRANT SELECT, UPDATE ON dbo.COLABORADOR TO RolRRHH;

-- Usuarios de prueba
CREATE USER UsuarioVendedor WITHOUT LOGIN;
CREATE USER UsuarioRRHH     WITHOUT LOGIN;
ALTER ROLE RolVendedor ADD MEMBER UsuarioVendedor;
ALTER ROLE RolRRHH     ADD MEMBER UsuarioRRHH;
GO

EXECUTE AS USER = 'UsuarioVendedor';
    SELECT nombre, cargo FROM COLABORADOR;   -- OK: columnas permitidas
REVERT;

EXECUTE AS USER = 'UsuarioVendedor';
    SELECT nombre, sueldo FROM COLABORADOR;  -- ERROR 230: permiso denegado en la columna sueldo
REVERT;

EXECUTE AS USER = 'UsuarioRRHH';
    SELECT nombre, sueldo FROM COLABORADOR;  -- OK
REVERT;
Buena práctica: los permisos se dan a los roles; las personas solo se agregan o se quitan de los roles. Cuando alguien cambia de puesto, basta con moverlo de rol.

Paso 9 — Consultar logins, usuarios, roles y permisos

-- ① Logins del servidor (S = SQL, U = usuario Windows, G = grupo Windows)
SELECT name, type_desc, default_database_name, is_disabled, create_date
FROM sys.server_principals
WHERE type IN ('S', 'U', 'G')
ORDER BY name;

USE FinancieraDemoBD;
GO

-- ② Usuarios y roles de la base de datos actual
SELECT name, type_desc, authentication_type_desc, create_date
FROM sys.database_principals
WHERE type IN ('S', 'U', 'R') AND principal_id > 4   -- omite dbo, guest, sys, INFORMATION_SCHEMA
ORDER BY type_desc, name;

-- ③ ¿Quién pertenece a qué rol?
SELECT r.name AS rol, m.name AS miembro
FROM sys.database_role_members rm
JOIN sys.database_principals r ON rm.role_principal_id   = r.principal_id
JOIN sys.database_principals m ON rm.member_principal_id = m.principal_id
ORDER BY rol, miembro;

-- ④ Permisos explícitos (GRANT / DENY) de cada usuario o rol
SELECT pr.name             AS principal,
       pe.state_desc        AS estado,       -- GRANT o DENY
       pe.permission_name   AS permiso,
       pe.class_desc        AS ambito,       -- DATABASE, OBJECT_OR_COLUMN, SCHEMA...
       OBJECT_NAME(pe.major_id) AS objeto
FROM sys.database_permissions pe
JOIN sys.database_principals pr ON pe.grantee_principal_id = pr.principal_id
WHERE pr.name IN ('UsuarioBDFinanciera', 'UsuarioApp', 'RolVendedor', 'RolRRHH')
ORDER BY principal, objeto;

-- ⑤ Permisos EFECTIVOS de un usuario sobre una tabla (incluye los heredados de roles)
EXECUTE AS USER = 'UsuarioVendedor';
    SELECT subentity_name AS columna, permission_name
    FROM fn_my_permissions('dbo.COLABORADOR', 'OBJECT');
REVERT;
Vistas antiguas que aún verás:
  • master..syslogins — lista de logins. Su columna password siempre aparece en NULL: las contraseñas se guardan cifradas (hash) y no se pueden leer. // SELECT sid, name, dbname, loginname FROM master..syslogins;
  • sysusers — usuarios de la base actual. // SELECT uid, name, sid FROM sysusers WHERE islogin = 1;
Son vistas de compatibilidad; en código nuevo usa sys.server_principals y sys.database_principals.

10. Implementación de políticas de contraseña

Los logins de SQL Server pueden heredar las directivas de contraseña de Windows (longitud mínima, complejidad, caducidad y bloqueo por intentos fallidos).

Opción¿Qué hace?
CHECK_POLICY = ONExige complejidad y aplica el bloqueo de cuenta tras varios intentos fallidos.
CHECK_EXPIRATION = ONLa contraseña caduca según la directiva de Windows. Requiere CHECK_POLICY = ON.
MUST_CHANGEObliga a cambiar la contraseña en el próximo inicio de sesión.
USE master;
GO

-- Cambiar la contraseña y activar políticas (observa las comas entre opciones)
ALTER LOGIN LoginFinanciera
WITH PASSWORD = N'Nueva#Clave2026',
     CHECK_POLICY = ON,         -- complejidad + bloqueo
     CHECK_EXPIRATION = ON;     -- la contraseña caduca
GO

-- Login nuevo que debe cambiar su contraseña al entrar por primera vez
CREATE LOGIN LoginPracticante
WITH PASSWORD = N'Temporal#2026' MUST_CHANGE,   -- MUST_CHANGE va pegado a la contraseña
     CHECK_POLICY = ON,
     CHECK_EXPIRATION = ON;                         -- obligatorio si se usa MUST_CHANGE
GO

-- Comprobación: qué logins tienen las políticas activas
SELECT name, is_policy_checked, is_expiration_checked,
       LOGINPROPERTY(name, 'IsMustChange')     AS debe_cambiar,
       LOGINPROPERTY(name, 'DaysUntilExpiration') AS dias_para_caducar
FROM sys.sql_logins
WHERE name IN ('LoginFinanciera', 'LoginPracticante');

-- Deshabilitar un login sin borrarlo (por ejemplo, un empleado de vacaciones)
ALTER LOGIN LoginPracticante DISABLE;   -- ENABLE para reactivarlo
Error frecuente: escribir las opciones sin coma (WITH PASSWORD = '...' CHECK_POLICY = ON) produce un error de sintaxis. Las opciones de WITH se separan siempre con comas; solo MUST_CHANGE va inmediatamente después de la contraseña, sin coma.

11. Gestión de permisos a nivel de sistema

Los permisos de servidor garantizan que solo las personas autorizadas puedan administrar el servidor. Se conceden desde master y siempre a un login (no a un usuario de base de datos). 

USE master;
GO

-- Permitir que el login cree y modifique otros logins
GRANT ALTER ANY LOGIN TO [LoginFinanciera];

-- Permitir ver el estado del servidor (sesiones, rendimiento) sin poder cambiar nada
GRANT VIEW SERVER STATE TO [LoginFinanciera];
GO

-- Comprobación: permisos de servidor del login
SELECT pr.name, pe.state_desc, pe.permission_name
FROM sys.server_permissions pe
JOIN sys.server_principals pr ON pe.grantee_principal_id = pr.principal_id
WHERE pr.name = 'LoginFinanciera';

-- Retirar el permiso cuando ya no se necesite
REVOKE ALTER ANY LOGIN FROM [LoginFinanciera];
Para recordar: en la tabla del resultado verás también CONNECT SQL: SQL Server lo concede automáticamente a cada login nuevo para que pueda conectarse.

12. Auditoría de eventos

La auditoría registra actividades del servidor o de la base de datos (quién se conectó, quién leyó una tabla sensible, quién falló al iniciar sesión). Se configura en tres piezas:

SERVER AUDIT ¿Dónde se guarda?
archivo, registro de Windows
+
SERVER AUDIT SPECIFICATION ¿Qué eventos del servidor?
inicios de sesión
+
DATABASE AUDIT SPECIFICATION ¿Qué acciones en la base?
SELECT, UPDATE sobre una tabla
Antes de ejecutar: crea la carpeta C:\Auditoria\ en el equipo del servidor. La cuenta del servicio de SQL Server debe poder escribir en ella. Necesitas ser sysadmin (o tener ALTER ANY SERVER AUDIT). 
USE master;
GO

-- ① El "contenedor": dónde se escriben los eventos
CREATE SERVER AUDIT AuditoriaInicioSesion
TO FILE (FILEPATH = 'C:\Auditoria\', MAXSIZE = 100 MB);
GO

-- ② Qué eventos de SERVIDOR se registran: inicios de sesión correctos y fallidos
CREATE SERVER AUDIT SPECIFICATION EspecInicioSesion
FOR SERVER AUDIT AuditoriaInicioSesion
    ADD (FAILED_LOGIN_GROUP),
    ADD (SUCCESSFUL_LOGIN_GROUP)
WITH (STATE = ON);
GO

-- ③ Activar la auditoría (se crea desactivada)
ALTER SERVER AUDIT AuditoriaInicioSesion WITH (STATE = ON);
GO

-- ④ Qué acciones de BASE DE DATOS se registran: quién consulta o modifica COLABORADOR
USE FinancieraDemoBD;
GO
CREATE DATABASE AUDIT SPECIFICATION EspecColaborador
FOR SERVER AUDIT AuditoriaInicioSesion
    ADD (SELECT, UPDATE ON dbo.COLABORADOR BY public)   -- public = cualquier usuario
WITH (STATE = ON);
GO

-- Prueba: generar un evento auditable
EXECUTE AS USER = 'UsuarioRRHH';
    SELECT nombre, sueldo FROM COLABORADOR;
REVERT;

-- Leer lo que quedó registrado en el archivo de auditoría
SELECT event_time, action_id, succeeded,
       server_principal_name, database_principal_name, object_name, statement
FROM sys.fn_get_audit_file('C:\Auditoria\*.sqlaudit', DEFAULT, DEFAULT)
ORDER BY event_time DESC;
Resultado: verás filas con action_id = 'SL' (SELECT) sobre COLABORADOR y el usuario que la ejecutó. Si te desconectas y vuelves a conectarte con LoginFinanciera, aparecerán filas LGIS (inicio de sesión correcto); un intento con contraseña errónea genera LGIF (fallido).
Importante: CREATE SERVER AUDIT solo crea el destino. Sin una especificación que diga qué eventos capturar, la auditoría queda activa pero no registra nada.

13. Control de acceso a datos sensibles

Los permisos deciden quién accede a una tabla; para proteger además el contenido de columnas sensibles existen dos técnicas complementarias:

Técnica ¿Qué hace? ¿El dato está cifrado? Dificultad
Enmascaramiento dinámico (Dynamic Data Masking) Muestra el dato oculto (aXXX@XXXX.com) a quien no tiene permiso UNMASK. No: solo se oculta al mostrarlo Baja — ideal para practicar
Always Encrypted El dato viaja y se guarda cifrado; solo la aplicación cliente con la llave puede leerlo. Sí: ni el administrador lo ve Alta — requiere llaves y configurar el cliente

13.1 Enmascaramiento dinámico de datos

USE FinancieraDemoBD;
GO

-- Ocultar email (formato de correo) y teléfono (muestra solo los 3 últimos dígitos)
ALTER TABLE CLIENTE ALTER COLUMN email
    ADD MASKED WITH (FUNCTION = 'email()');
ALTER TABLE CLIENTE ALTER COLUMN telefono
    ADD MASKED WITH (FUNCTION = 'partial(0,"XXX-XXX-",3)');

-- Ocultar el sueldo (los números se muestran como 0)
ALTER TABLE COLABORADOR ALTER COLUMN sueldo
    ADD MASKED WITH (FUNCTION = 'default()');
GO

-- Prueba 1: el vendedor ve los datos enmascarados
EXECUTE AS USER = 'UsuarioVendedor';
    SELECT nombre, email, telefono FROM CLIENTE;   -- aXXX@XXXX.com | XXX-XXX-321
REVERT;

-- Prueba 2: RR.HH. necesita ver el sueldo real → permiso UNMASK
GRANT UNMASK TO RolRRHH;
EXECUTE AS USER = 'UsuarioRRHH';
    SELECT nombre, sueldo FROM COLABORADOR;        -- valores reales
REVERT;

-- Ver qué columnas están enmascaradas
SELECT OBJECT_NAME(object_id) AS tabla, name AS columna, masking_function
FROM sys.masked_columns;
Para recordar: los usuarios con db_owner o sysadmin siempre ven los datos reales. Por eso, al probar como administrador sin EXECUTE AS, no notarás ningún cambio.

13.2 Always Encrypted (demostrativo)

Always Encrypted cifra la columna con una llave de cifrado de columna (CEK) protegida a su vez por una llave maestra de columna (CMK) que vive fuera de SQL Server (por ejemplo, en el almacén de certificados de Windows). Las llaves se crean más fácilmente con el asistente de SSMS: clic derecho sobre la tabla → Cifrar columnas... 

-- Requiere que la llave LlaveEncriptacion ya exista (creada con el asistente de SSMS)
ALTER TABLE dbo.COLABORADOR
ADD numero_cuenta VARCHAR(30)
    COLLATE Latin1_General_BIN2                          -- obligatorio para cifrado determinista de texto
    ENCRYPTED WITH (
        COLUMN_ENCRYPTION_KEY = LlaveEncriptacion,
        ENCRYPTION_TYPE = DETERMINISTIC,                 -- mismo valor → mismo cifrado (permite WHERE =)
        ALGORITHM = 'AEAD_AES_256_CBC_HMAC_SHA_256'    -- el algoritmo va entre comillas
    ) NULL;
Determinista vs aleatorio: DETERMINISTIC genera siempre el mismo valor cifrado para el mismo dato, lo que permite búsquedas por igualdad, pero puede revelar patrones. RANDOMIZED es más seguro, pero no permite buscar ni agrupar por esa columna.

14. Limpieza del entorno

Al terminar la práctica conviene eliminar lo creado. El orden importa: primero lo que depende de otra cosa. 

-- ① Auditoría de base de datos: desactivar y eliminar
USE FinancieraDemoBD;
GO
ALTER DATABASE AUDIT SPECIFICATION EspecColaborador WITH (STATE = OFF);
DROP DATABASE AUDIT SPECIFICATION EspecColaborador;
GO

-- ② Auditoría de servidor: especificación primero, auditoría después
USE master;
GO
ALTER SERVER AUDIT SPECIFICATION EspecInicioSesion WITH (STATE = OFF);
DROP SERVER AUDIT SPECIFICATION EspecInicioSesion;
ALTER SERVER AUDIT AuditoriaInicioSesion WITH (STATE = OFF);
DROP SERVER AUDIT AuditoriaInicioSesion;
GO

-- ③ Usuarios (dentro de la base) ANTES que los logins
USE FinancieraDemoBD;
GO
DROP USER IF EXISTS UsuarioBDFinanciera;
DROP USER IF EXISTS UsuarioApp;
DROP USER IF EXISTS UsuarioVendedor;
DROP USER IF EXISTS UsuarioRRHH;
DROP ROLE IF EXISTS RolVendedor;     -- un rol solo se elimina si ya no tiene miembros
DROP ROLE IF EXISTS RolRRHH;
GO

-- ④ Logins (en master)
USE master;
GO
IF EXISTS (SELECT 1 FROM sys.server_principals WHERE name = 'LoginFinanciera')
    DROP LOGIN LoginFinanciera;
IF EXISTS (SELECT 1 FROM sys.server_principals WHERE name = 'LoginPracticante')
    DROP LOGIN LoginPracticante;
GO
¿Por qué el usuario antes que el login? SQL Server permite borrar un login aunque tenga usuarios enlazados, pero esos usuarios quedan huérfanos (sin login asociado) dentro de cada base de datos. Borrar primero el usuario evita dejar restos. La base FinancieraDemoBD no se elimina: se usará en los ejercicios.

• Login para entrar al servidor; usuario para entrar a la base de datos.

Ejercicio 1 — Login y usuario para el cajero

Enunciado:

Crear el login LoginCajero (autenticación SQL Server, con política de contraseña) y su usuario UsuarioCajero en FinancieraDemoBD. El cajero solo puede leer la tabla CLIENTE y ejecutar spInsertar_Cliente. Comprobar que no puede eliminar clientes.

Tablas involucradas: CLIENTE
Pistas:
  • El login se crea en master; el usuario, en FinancieraDemoBD.
  • Usa IF NOT EXISTS con sys.server_principals y sys.database_principals.
  • Dos GRANT: uno de SELECT sobre la tabla y otro de EXECUTE sobre el procedimiento.
  • Prueba un DELETE dentro de EXECUTE AS USER: debe fallar.
Ver solución 
USE master;
GO
IF NOT EXISTS (SELECT 1 FROM sys.server_principals WHERE name = N'LoginCajero')
    CREATE LOGIN LoginCajero WITH PASSWORD = N'Cajero#2026',
                             DEFAULT_DATABASE = FinancieraDemoBD,
                             CHECK_POLICY = ON;
GO

USE FinancieraDemoBD;
GO
IF NOT EXISTS (SELECT 1 FROM sys.database_principals WHERE name = N'UsuarioCajero')
    CREATE USER UsuarioCajero FOR LOGIN LoginCajero;

GRANT SELECT ON dbo.CLIENTE TO UsuarioCajero;              -- solo lectura de la tabla
GRANT EXECUTE ON spInsertar_Cliente TO UsuarioCajero;        -- inserta solo vía procedimiento
GO

EXECUTE AS USER = 'UsuarioCajero';
    SELECT * FROM CLIENTE;                                              -- OK
    EXEC spInsertar_Cliente 'Pedro Gómez', '43215678', 'pedro@mail.com'; -- OK
REVERT;

REVERT;

Ejercicio 2 — Rol auditor de solo lectura sin datos salariales

Enunciado:

Crear el rol RolAuditor que pueda leer CLIENTE y PROVEEDOR completos, y de COLABORADOR solo nombre y cargo. Crear el usuario UsuarioAuditor sin login, agregarlo al rol y comprobar que no puede ver sueldo ni modificar ninguna tabla.

Tablas involucradas: CLIENTE, PROVEEDOR y COLABORADOR
Pistas:
  • CREATE ROLE y luego los GRANT al rol, no al usuario.
  • Permiso por columnas: GRANT SELECT ON tabla (col1, col2) TO rol.
  • CREATE USER ... WITHOUT LOGIN y ALTER ROLE ... ADD MEMBER.
  • Verifica con fn_my_permissions('dbo.COLABORADOR', 'OBJECT').
Ver solución 
USE FinancieraDemoBD;
GO
CREATE ROLE RolAuditor;
GRANT SELECT ON dbo.CLIENTE   TO RolAuditor;

CREATE USER UsuarioAuditor WITHOUT LOGIN;
ALTER ROLE RolAuditor ADD MEMBER UsuarioAuditor;
GO

EXECUTE AS USER = 'UsuarioAuditor';
    SELECT nombre, cargo FROM COLABORADOR;                          -- OK
    SELECT subentity_name, permission_name
    FROM fn_my_permissions('dbo.COLABORADOR', 'OBJECT');           -- solo nombre y cargo

    SELECT sueldo FROM COLABORADOR;                                 -- ERROR 230

Ejercicio 3 — DENY sobre un rol fijo

Enunciado:

Crear el usuario UsuarioOperador (sin login) como miembro de db_datareader y db_datawriter. La empresa decide que no puede eliminar proveedores, pero sí debe seguir eliminando otros registros. Aplicarlo, comprobarlo y luego deshacer la restricción.

Tablas involucradas: PROVEEDOR y CLIENTE
Pistas:
  • No se puede “quitar” un permiso de un rol fijo para una sola tabla con REVOKE: hay que usar DENY.
  • Para comprobar el DELETE sin perder datos, envuélvelo en una transacción con ROLLBACK.
  • Para deshacer: REVOKE DELETE ON ... FROM ....
Ver solución 
USE FinancieraDemoBD;
GO
CREATE USER UsuarioOperador WITHOUT LOGIN;
ALTER ROLE db_datareader ADD MEMBER UsuarioOperador;
ALTER ROLE db_datawriter ADD MEMBER UsuarioOperador;

DENY DELETE ON dbo.PROVEEDOR TO UsuarioOperador;   -- gana sobre db_datawriter
GO

EXECUTE AS USER = 'UsuarioOperador';
    DELETE FROM PROVEEDOR WHERE id_proveedor = 3;      -- ERROR 229
REVERT;

EXECUTE AS USER = 'UsuarioOperador';
    BEGIN TRANSACTION;
        DELETE FROM CLIENTE WHERE id_cliente = 5;      -- OK: en CLIENTE no hay DENY
    ROLLBACK;                                         -- deshace el borrado de prueba
REVERT;

-- Quitar la restricción: vuelve a valer db_datawriter
REVOKE DELETE ON dbo.PROVEEDOR FROM UsuarioOperador;
