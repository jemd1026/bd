Laboratorio: La sentencia MERGE

Gestión de Datos e Información · Trabajo en casa

1. Indicaciones generales

Objetivo: usar MERGE para sincronizar tablas, hacer upserts, depurar cargas de datos con errores y mantener tablas de resumen, aplicando las buenas prácticas vistas en clase.

  • Modalidad: individual.
  • Escenario: el sistema académico de una universidad (estudiantes, cursos y notas). La base de datos se crea con el script de la sección 3.
  • Material de apoyo: la guía de MERGE.
  • Herramientas: SQL Server (Express o Developer) y SQL Server Management Studio (SSMS).
  • Orden: resuelve los ejercicios en orden; cada uno parte del resultado del anterior.
  • Entrega: un script .sql y un informe .pdf con las evidencias (sección 5).
Regla de personalización (obligatoria): reemplaza APELLIDO por tu primer apellido en mayúsculas, sin tildes ni espacios (por ejemplo, LabMERGE_PEREZ, spRegistrarNota_PEREZ). En los bloques de código, lo que debes reemplazar aparece en naranja. Además, en el ejercicio 1 te agregarás a ti mismo como estudiante. Un ejercicio con nombres sin personalizar no se califica.

Crea la base de datos y carga los datos iniciales. Si te equivocas en algún ejercicio, puedes volver a ejecutar este script completo para empezar de cero (se pierde todo lo avanzado).

-- ① Padrón oficial de estudiantes (DESTINO del ejercicio 1)
CREATE TABLE Estudiante (
    codigo    CHAR(8)      PRIMARY KEY,
    nombres   VARCHAR(60)  NOT NULL,
    apellidos VARCHAR(60)  NOT NULL,
    email     VARCHAR(100) NULL,                        -- admite NULL (¡ojo al comparar!)
    carrera   VARCHAR(40)  NOT NULL,
    estado    CHAR(1)      NOT NULL DEFAULT 'A'
              CHECK (estado IN ('A', 'I'))              -- A = activo, I = inactivo
);

-- ② Archivo que envía Admisión cada ciclo (ORIGEN del ejercicio 1, sin clave primaria)
CREATE TABLE Estudiante_Carga (
    codigo    CHAR(8)      NOT NULL,
    nombres   VARCHAR(60)  NOT NULL,
    apellidos VARCHAR(60)  NOT NULL,
    email     VARCHAR(100) NULL,
    carrera   VARCHAR(40)  NOT NULL
);

-- ③ Cursos
CREATE TABLE Curso (
    id_curso INT         PRIMARY KEY,
    nombre   VARCHAR(60) NOT NULL,
    creditos INT         NOT NULL
);

-- ④ Notas oficiales (una por estudiante y curso)
CREATE TABLE Nota (
    codigo         CHAR(8)      NOT NULL REFERENCES Estudiante(codigo),
    id_curso       INT          NOT NULL REFERENCES Curso(id_curso),
    nota           DECIMAL(4,2) NOT NULL CHECK (nota BETWEEN 0 AND 20),
    fecha_registro DATETIME2    NOT NULL DEFAULT SYSDATETIME(),
    PRIMARY KEY (codigo, id_curso)
);

-- ⑤ Carga masiva de notas desde un Excel (ORIGEN del ejercicio 3, puede traer errores)
CREATE TABLE Nota_Carga (
    id_carga INT IDENTITY(1,1) PRIMARY KEY,             -- orden de llegada de cada fila
    codigo   CHAR(8),
    id_curso INT,
    nota     DECIMAL(4,2)
);

-- ⑥ Lista completa del curso 2 que envía su docente (ORIGEN del ejercicio 4)
CREATE TABLE Nota_Carga_Curso2 (
    codigo CHAR(8),
    nota   DECIMAL(4,2)
);

-- ⑦ Resumen por curso, calculado hace tiempo (DESTINO del ejercicio 5)
CREATE TABLE ResumenCurso (
    id_curso      INT PRIMARY KEY,
    cantidad      INT,
    promedio      DECIMAL(4,2),
    aprobados     INT,
    fecha_calculo DATETIME2
);

-- ⑧ Bitácora de sincronizaciones (recibe OUTPUT INTO: sin FK, CHECK ni triggers)
CREATE TABLE LogSincronizacion (
    id_log        INT IDENTITY(1,1) PRIMARY KEY,
    proceso       VARCHAR(30),
    accion        NVARCHAR(10),
    clave         VARCHAR(30),
    valor_antes   VARCHAR(200),
    valor_despues VARCHAR(200),
    usuario       VARCHAR(100) DEFAULT SUSER_SNAME(),
    fecha         DATETIME2    DEFAULT SYSDATETIME()
);
GO

4. Ejercicios

Ejercicio 1 — Sincronizar el padrón de estudiantes con baja lógica

Enunciado:

Admisión envía el padrón del nuevo ciclo en Estudiante_Carga. Hay que dejar Estudiante al día, pero nunca se borra un estudiante (tiene notas asociadas): quien no llega en el padrón pasa a inactivo.

  1. Agrega a Estudiante_Carga una fila con tus datos reales (nombres, apellidos, tu carrera) y el código 20249999.
  2. Antes de sincronizar, escribe una consulta con FULL OUTER JOIN que muestre, para cada código, la acción que debería aplicarse: INSERT, UPDATE, REACTIVAR, DESACTIVAR o sin cambios.
  3. Escribe un MERGE que:
    • actualice nombres, apellidos, email y carrera solo si algo cambió, tomando en cuenta que email puede ser NULL;
    • reactive (estado = 'A') a quien estaba inactivo y volvió a aparecer;
    • inserte a los nuevos con estado = 'A';
    • marque como inactivo (estado = 'I') a quien no vino en el padrón y estaba activo;
    • registre cada acción en LogSincronizacion con proceso = 'PADRON', la clave (código) y el estado/email antes y después.
Pistas:
  • Comparación segura con NULL: WHEN MATCHED AND EXISTS (SELECT ... EXCEPT SELECT ...) (guía, sección 9.2). Si incluyes estado en la comparación, la reactivación queda resuelta en la misma cláusula.
  • En WHEN NOT MATCHED BY SOURCE se puede usar UPDATE con una condición AND.
  • OUTPUT admite constantes y expresiones: // OUTPUT 'PADRON', $action, COALESCE(inserted.codigo, deleted.codigo), CONCAT(deleted.estado, ' | ', deleted.email), ... INTO LogSincronizacion (...)
Evidencias:
  • E1.1 Consulta de identificación + resultado de tu consulta de predicción (FULL OUTER JOIN), donde se vea tu fila 20249999.
  • E1.2 El MERGE ejecutado y el mensaje de filas afectadas.
  • E1.3 Estudiante después del MERGE y las filas de LogSincronizacion del proceso PADRON.

Pregunta: si hubieras comparado con destino.email <> origen.email, ¿qué habría pasado con María López (20240003)? ¿Y por qué aquí no se puede usar DELETE?

Ejercicio 2 — Registro de notas con un procedimiento upsert

Enunciado:

Los docentes registran notas una por una desde la aplicación, sin saber si la nota ya existe.

  1. Crea spRegistrarNota_APELLIDO con los parámetros @codigo, @id_curso y @nota, que:
    • rechace con un error propio las notas fuera del rango 0–20;
    • con un solo MERGE, inserte la nota si no existe o la actualice (con su fecha_registro) si existe y es distinta;
    • sea seguro si dos docentes guardan la misma nota al mismo tiempo;
    • registre la acción en LogSincronizacion con proceso = 'NOTA_INDIVIDUAL', la clave codigo-curso y la nota antes y después.
  2. Pruébalo con tu código 20249999: registra tu nota en el curso 2, corrígela, vuelve a enviar el mismo valor y finalmente intenta registrar un 25.
Pistas:
  • Validación: IF @nota NOT BETWEEN 0 AND 20 THROW 50001, '...', 1;
  • Origen de una sola fila: USING (SELECT @codigo AS codigo, @id_curso AS id_curso, @nota AS nota) AS origen.
  • Concurrencia: MERGE INTO Nota WITH (HOLDLOCK) AS destino (guía, sección 10.2).
  • Clave compuesta en el ON: compara codigo y id_curso.
Evidencias:
  • E2.1 Código completo del procedimiento en el editor de SSMS.
  • E2.2 Las 4 pruebas con su resultado: inserción, corrección, mismo valor (sin cambios) y el error de la nota 25.
  • E2.3 Filas de LogSincronizacion del proceso NOTA_INDIVIDUAL.

Pregunta: ¿qué podría pasar sin HOLDLOCK si dos docentes registran al mismo tiempo la primera nota del mismo estudiante en el mismo curso?

Ejercicio 3 — Carga masiva de notas con datos sucios

Enunciado:

Un docente subió un Excel a Nota_Carga. El archivo trae problemas: filas repetidas para el mismo estudiante y curso, estudiantes o cursos que no existen y notas fuera de rango.

  1. Ejecuta primero un MERGE ingenuo de Nota_Carga hacia Nota (insertar o actualizar, sin depurar nada) y registra el error que se produce.
  2. Escribe una consulta de rechazados que liste las filas de Nota_Carga que no deben cargarse, con una columna motivo (“estudiante no existe”, “curso no existe”, “nota fuera de rango”, “duplicado descartado”).
  3. Escribe el MERGE corregido: de cada par estudiante–curso repetido conserva solo la última fila cargada, descarta las filas inválidas, actualiza solo si la nota cambió e inserta las nuevas. Muestra con OUTPUT lo que hizo.
Pistas:
  • “La última fila cargada” es la de mayor id_carga: ROW_NUMBER() OVER (PARTITION BY codigo, id_curso ORDER BY id_carga DESC).
  • Valida la existencia con EXISTS (SELECT 1 FROM Estudiante ...) y EXISTS (SELECT 1 FROM Curso ...).
  • Una CTE puede ir antes del MERGE: WITH origen_limpio AS (...) MERGE INTO Nota ... (guía, sección 12.2).
  • Si el MERGE ingenuo no da el error que esperas, lee el mensaje con atención: puede fallar por otra regla de la tabla. Explica en el informe cuál fue.
Evidencias:
  • E3.1 Consulta de identificación + el MERGE ingenuo con su mensaje de error.
  • E3.2 Resultado de la consulta de rechazados con la columna motivo.
  • E3.3 OUTPUT del MERGE corregido y las notas del curso 1 después de la carga.

Pregunta: ¿por qué conservaste la última fila y no la primera o la nota más alta? ¿Qué riesgo tiene escoger mal ese criterio?

Ejercicio 4 — Origen parcial: la lista de un solo curso

Enunciado:

La docente de Gestión de Datos (curso 2) envía en Nota_Carga_Curso2 la lista completa y definitiva de su curso: quien no aparece se retiró y su nota debe eliminarse. Las notas de los demás cursos no deben tocarse.

  1. Muestra la cantidad de notas por curso antes de sincronizar.
  2. Dentro de BEGIN TRANSACTION, ejecuta una versión ingenua cuyo destino sea toda la tabla Nota con WHEN NOT MATCHED BY SOURCE THEN DELETE. Observa con OUTPUT cuántas notas eliminaría y deshaz con ROLLBACK.
  3. Escribe la versión correcta, que limite el destino al curso 2, actualice las notas que cambiaron, inserte las nuevas y elimine las de los retirados.
  4. Muestra la cantidad de notas por curso después.
Pistas:
  • Limitar el destino con una CTE: WITH notas_curso2 AS (SELECT * FROM Nota WHERE id_curso = 2) MERGE INTO notas_curso2 ... (guía, sección 12.3).
  • El origen no trae id_curso: en el INSERT debes escribir el 2 de forma explícita.
  • No filtres el curso dentro del ON: revisa por qué en la nota de la sección 12.3 de la guía.
Evidencias:
  • E4.1 Consulta de identificación + cantidad de notas por curso antes.
  • E4.2 OUTPUT de la versión ingenua (cuántos DELETE habría hecho) y el ROLLBACK.
  • E4.3 OUTPUT de la versión correcta y la cantidad de notas por curso después.

Pregunta: en un sistema real, ¿qué consecuencias habría tenido ejecutar la versión ingenua sin transacción? Propón una medida para que no vuelva a ocurrir.

Ejercicio 5 — Tabla de resumen: MERGE vs sentencias separadas

Enunciado:

ResumenCurso está desactualizada: le falta un curso, tiene datos viejos y contiene un curso que ya no existe. Debe quedar con, por cada curso que tenga notas: cantidad de notas, promedio y cantidad de aprobados (nota ≥ 11).

  1. Guarda una copia del estado actual: SELECT * INTO ResumenCurso_Copia FROM ResumenCurso;
  2. Actualiza ResumenCurso con un solo MERGE cuyo origen sea una consulta agrupada sobre Nota. La fecha_calculo debe quedar con la fecha y hora actuales.
  3. Actualiza ResumenCurso_Copia con el mismo resultado, pero usando UPDATE, INSERT y DELETE separados dentro de una transacción.
  4. Demuestra con una consulta que ambas tablas quedaron idénticas (sin contar fecha_calculo).
Pistas:
  • Origen agrupado: // SELECT id_curso, COUNT(*), CAST(AVG(nota) AS DECIMAL(4,2)), SUM(CASE WHEN nota >= 11 THEN 1 ELSE 0 END) FROM Nota GROUP BY id_curso
  • Para no repetir la consulta agrupada en las tres sentencias, guárdala antes en una tabla temporal #resumen.
  • Dos tablas son idénticas si A EXCEPT B y B EXCEPT A devuelven 0 filas.
Evidencias:
  • E5.1 Consulta de identificación + ResumenCurso antes y después del MERGE.
  • E5.2 La versión con sentencias separadas ejecutada y sus mensajes de filas afectadas.
  • E5.3 La consulta de comparación devolviendo 0 filas.

Pregunta: después de escribir ambas versiones, ¿cuál preferirías mantener en un sistema real y por qué? Menciona al menos una ventaja de cada una.
